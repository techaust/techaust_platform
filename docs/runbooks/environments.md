### Rolling back the fourth admin Worker on staging (owner's Q2 A, 2026-11-02; early check finding 2)
If the split misbehaves on staging, the lead may roll back straight away and tell the owner afterwards (staging only). **Only one order is safe: the admin finance Worker first, then jobs, then the admin front. Leave the admin invoices Worker and the admin API in place.**
1. **Admin finance first** (`techaust-platform-admin-finance-staging`). The old finance version answers every admin row (invoices included) and exports `BillingJobs` and `GatewayEvents` with `issueGatewayAdvance`. While the front and jobs are still new, they keep working against it: the new front sends invoice rows to the invoices Worker and payments rows to the old finance, which answers them; the new jobs calls `ADMIN_GATEWAY` (`processEvent`, `refreshCheckout`, which the old finance has) and the invoices Worker for `ADMIN_JOBS` and `ADMIN_ADVANCE`.
2. **Then jobs** (`techaust-platform-jobs-staging`). The old jobs calls `BillingJobs` and `GatewayEvents.issueGatewayAdvance` on the finance Worker, which only the old finance has. Rolled back before finance, every `care.bill` and `gateway.advance` message would fail against the new finance and end as dead letters ("Needs review" items and the Owner's bell).
3. **Then the admin front** (`techaust-platform-admin-staging`). The old front sends the invoice, statement, report, approval and dashboard rows to `ADMIN_FINANCE`. Rolled back before finance, those rows would answer 404 from the new finance (deny by default).
4. **Leave the admin invoices Worker and the admin API.** Once the three above are old, nothing calls the invoices Worker, so it does no harm; the API's routes did not change in the split.

Each step: Workers & Pages › the Worker › Deployments › the previous version › Rollback, or `pnpm exec wrangler rollback <version-id> --name <worker> -m "<reason>"` from `apps/admin` (or `apps/jobs`). There are no migrations in the split, so the shared D1 needs nothing (a rollback never reverts data). Then run the health checks by hand (`node scripts/staging-health.mjs admin`, `… jobs`) with the deploy-check token. A later deploy from `main` brings all seven back in the Q1 order.

Limit of the step split (A1 5): a step without the token can't read it, but steps share the runner, so a malicious package in a build step could still leave files or `GITHUB_ENV` entries behind for a later step. The stronger form (a separate deploy job that receives the built files and installs only wrangler) is a possible follow-up, not built.

### Health checks after a deploy (A6 8)
`node scripts/staging-health.mjs <app>` asks the Worker's health route through Cloudflare Access with a service token (`CF-Access-Client-Id` and `-Secret` headers), retries for about 30 seconds, and fails the job unless the Worker itself answers: its JSON with `ok: true`, its own `service` name and `env: "staging"`. A redirect to the Access sign-in page or a non-JSON 401/403 from Access counts as a failure. The checks per app: admin `GET /api/v1/health` = 200, a signed-out `GET /api/v1/leads` = the API Worker's JSON 401 (proves the `ADMIN_API` binding), a signed-out `GET /api/v1/dashboard` = the invoices Worker's JSON 401 (proves `ADMIN_INVOICES`; the finance Worker's from M6.1 until the fourth admin Worker) and a signed-out `GET /api/v1/payments` = the finance Worker's JSON 401 (proves `ADMIN_FINANCE`); a 502 fails, portal `GET /api/v1/health`, jobs `GET /healthz`, web `GET /api/health` (M7.5 C4; `/api/geo` before).
- **All four apps: on**, with the deploy-check service token `staging-deploy-check` (`CF_ACCESS_DEPLOY_CLIENT_ID`, `CF_ACCESS_DEPLOY_CLIENT_SECRET`; a Service Auth policy on each of the four staging Access apps; owner, 2026-10-30; Part 4 of [access-staging.md](access-staging.md)). Made for 1 year: renew it before it lapses or the deploy fails at the first check. The benchmark token stays for the benchmark only.

### ERASURE_HASH_KEY (M7.4, L23; owner step H1)
The key of the erased-address hash: an erasure keeps only HMAC-SHA256(key, the lower-cased address), never the address (the `h:` stop in `email_suppressions`, `contacts.erased_hash`, `leads.erased_hash`, `consent_receipts.subject_hash`; Settled by the lead on the safest reading, 2026-11-06 (08-C RB-46)). **The same value must be on two Workers:** the admin API (`techaust-platform-admin-api-staging`: the erase, anonymise, lead erase and "Allow emails again"; its ONLY secret, `scripts/check-worker-config.mjs`) and jobs (`techaust-platform-jobs-staging`: the email consumer's stop, the lead purge, the hash fill). Both list it in `secrets.required`, so a deploy without it fails.

**The jobs Worker's required secrets on staging** (`env.staging.secrets.required`; a deploy fails while any is missing): `SES_ACCESS_KEY_ID`, `SES_SECRET_ACCESS_KEY`, `RAZORPAY_WEBHOOK_SECRET`, `STRIPE_WEBHOOK_SECRET`, `PAYPAL_WEBHOOK_ID`, `SES_EVENTS_TOKEN`, `UNSUBSCRIBE_KEY`, `ERASURE_HASH_KEY` and, from M7.5, `CF_ANALYTICS_TOKEN` (`scripts/set-cf-analytics-token.ps1`).

Setting it (the owner, once, before the M7.4 PR merges):
1. Open PowerShell (Start menu, type "PowerShell", press Enter).
2. Run, in one line:
   ```
   powershell -ExecutionPolicy Bypass -File "D:\Business\1. Parent Project\TecHaust Technologies\Application\techaust_platform\scripts\set-erasure-hash-key.ps1"
   ```
3. Type `YES` and press Enter. The script makes 32 random bytes, puts the same value on both staging Workers with `wrangler secret put`, never shows or copies it, and prints one line starting `RESULT:`. Copy back **only that line**.

**Checking that both Workers hold the same key** (M7.4 early check 2 M3): the key can't be read back, so the only proof is an erased address being stopped by jobs. Do this once after H1 has merged and staging has deployed, and again after any change of the key on either Worker. The lead runs it with the owner (the Owner's sign-in and a fresh code are needed); only made-up `@example.test` data.
1. Pick a fresh made-up address that nothing on staging holds yet, for example `keycheck-20261107@example.test` (the date of the check; a new one each time).
2. Add it as a contact of sample client A, in one line in PowerShell:
   ```
   pnpm --dir "D:\Business\1. Parent Project\TecHaust Technologies\Application\techaust_platform" portal:sample --staging --email keycheck-20261107@example.test
   ```
3. In the staging admin, open sample client A, open that contact, choose **Erase** (not anonymise), give the reason "key check", and confirm with a fresh code. The address has no other live holder (no other contact or unconverted lead), so the admin API writes the erased-address stop with **its** key.
4. On the staging website, send the contact form with that same address (any made-up name and message). The jobs Worker queues the acknowledgement email to it and checks the stop with **its** key.
5. In the staging admin, open **Email log** and find the newest `lead.acknowledgement` row to that address (the address shows as written on the form). Expected: status **Skipped** with the error `erased`. The Owner also gets one `email.erased_skip` bell naming the new lead's reference (the lead is a live holder, L25): expected.
   - Skipped with the error `recipient not in allow-list` (or any error other than `erased`), or **Sent**: the two Workers hold **different keys**. Stop and tell the lead; don't run the script again (see "Losing or changing the key" below).
6. Clean up: in the admin, open the new lead and **Erase** it (Owner, fresh code). The sample client A's erased contact stays erased; nothing else is left.

Locally, `pnpm dev:secrets` writes one fixed, made-up value into both `apps/admin/.dev.vars` and `apps/jobs/.dev.vars` (they must match); the tests inject their own made-up value.

**Losing or changing the key.** The key can't be read back from Cloudflare, and it can't be rebuilt: every stop already written is the hash under the old key, and the addresses it was made from are gone. With a new key (a second run of the script, a rotation, a new Worker without the old value) those stops no longer match, so **people erased before could be emailed again**, and their consent receipts no longer link to a returning person. So: run the script once per environment, never "to be safe"; if a Worker ever loses the secret (a deploy fails with it missing), stop and ask the lead before setting anything. A planned change of key needs its own task (both keys held for a while, every stored hash moved over in a job), never a plain re-run. Production gets its own key at Phase 7 (owner's yes then).

Repository: the secret `CLOUDFLARE_ACCOUNT_ID`; the variables `PRODUCTION_ENABLED` (must be `true` for any production deploy), `AWS_BACKUP_ROLE_ARN`, `BACKUP_BUCKET`, `BACKUP_PUBLIC_KEY_PEM`.

### The production deploy (`.github/workflows/deploy-prod.yml`)
Run by the owner only: GitHub › Actions › **Deploy production** › Run workflow, **"Use workflow from: main"**, with:
- `tag`: `main` (default) or a `v*` release tag on main;
- `confirm`: exactly `deploy techaust.com <tag>`;
- `stage`: `full` (default) or `database`;
- `check_web`: `true` (default); `false` until techaust.com is attached to the website Worker.

The jobs, in order:
1. **guard:** the owner (`techaust`, both the starter and any re-runner), `PRODUCTION_ENABLED` = `true`, the typed confirmation, and `main` or a `v*` tag. Anything else stops the run before anything is built.
2. **snapshot** (stage `full` only; P7 ops): in the `backup` environment, wrangler alone, it **reads** the newest published catalogue snapshot from the production D1 (`scripts/fetch-catalogue-snapshot.mjs --env production`). A published list goes to the build as an artifact; none published (the first deploys) means the website is built from the seed. A snapshot that exists but can't be read, or whose SHA-256 doesn't match, fails the run: production never falls back to the seed silently. It needs the `site_snapshots` table, so run stage `database` once before the first `full` run on a new database (the launch order does).
3. **build** (no environment, no secret): the snapshot into `apps/web`, then the seed SQL, the production builds of the admin, the portal and the website (the web build validates the snapshot with the core zod schema), the pre-bundled jobs and website Workers, the `.dev.vars` check, and on stage `full` the pre-production readiness check (`scripts/check-prod-readiness.mjs`). The commit it built is recorded and must be on `main`.
4. **deploy** (the `production` environment: **the owner approves here**, once): wrangler alone; the build placed by `scripts/place-build-artifact.mjs` and checked as a production build; the D1 Time Travel bookmark written into the job summary (the restore point); the migrations; the seed (insert-only). Stage `database` stops here. Stage `full` then deploys one Worker per step: **admin API, admin invoices, admin finance, admin front, portal, jobs, website**, with a health check (`scripts/prod-health.mjs`) after the admin front (`/api/v1/health` through the Access bypass), the portal (`/api/v1/health`), jobs (`/healthz` and the webhook paths' own refusals) and the website (`/api/health`, only when `check_web` is true). Each answer must be the Worker's own JSON with `env: "production"`; the check retries for about two minutes (a new custom domain may take a minute). A failed step stops the job, so nothing deploys after a failed Worker.

**After publishing prices in the production admin** (Catalogue › Publish), the website still shows the old prices until the next production deploy: run **Deploy production** with `stage: full` (same `tag`, `confirm` and approval as any deploy). Production never takes the 30-minute staging publisher (`publish-catalogue.yml` is staging only; owner's rule in its header).

### Rollback (08 §6.3; [incident.md](incident.md) §2.8)
- **Code:** `wrangler rollback --name techaust-platform-<app> --env production`, or Workers & Pages › the Worker › Deployments › the previous version › Rollback. Roll back only the Workers a release changed, callers first: website, jobs, portal, admin front, admin finance, admin invoices, admin API (the reverse of the deploy order). Migrations are backward-compatible (05 §5.5), so a code rollback never needs a database rollback. Then re-run `node scripts/prod-health.mjs <app>` for each app rolled back.
- **Data:** never rolled back by a code rollback. A bad migration or a damaged database: D1 Time Travel from the bookmark in the deploy's job summary ([restore.md](restore.md) §2), the owner's yes first.
- **The old site:** `techaust-web` was deleted on 2026-11-07 (owner); there is no fallback to it. A website problem is fixed forward or the new `web` Worker is rolled back.

### Backups ([restore.md](restore.md) §3)
- **Nightly:** `.github/workflows/backup.yml` at 21:10 UTC (02:40 IST) exports the production D1, encrypts it for the owner's RSA key and uploads it to `s3://<BACKUP_BUCKET>/daily/` (ap-south-1), kept 90 days by the bucket's lifecycle rule (60 + 30 days on the versioned bucket; [restore.md](restore.md) §3.1). The export's signed download link never reaches the public log.
- **Monthly, kept 10 years:** the run on the 1st of each month (UTC), any nightly run while the month has no copy yet (a missed or failed 1st is caught up), or a run by hand with **monthly** ticked, also uploads the finance-only copy to `monthly/` (each copy named by the run's UTC time, never replaced) ([restore.md](restore.md) §3.6; the AWS policy and lifecycle changes are in §3.6.4).
- **Restore drill:** [restore.md](restore.md) §3.4; `scripts/backup-verified.json` records it, and the readiness check blocks stage `full` until it does.
