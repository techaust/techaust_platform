Deploys happen automatically when a PR is merged to `main` (`.github/workflows/deploy-staging.yml`, owner's yes 2026-10-30 for full audit A1 5 and A6 8):
1. `pnpm install`, then the seed SQL is written (`pnpm --filter @techaust/db seed:sql`), **without** the Cloudflare token.
2. With the token: `wrangler d1 migrations apply DB --remote --env staging`, the seed (`wrangler d1 execute`), and the published catalogue snapshot read.
3. **Without** the token: the staging builds, `build:staging` in admin, portal and web (`CLOUDFLARE_ENV=staging vite build` or `astro build`, with the header and dist checks). Every step that runs package code runs without `CLOUDFLARE_API_TOKEN`; only the credentials check and the wrangler steps get it (step-level `env`). `publish-catalogue.yml` builds the website the same way.
4. With the token, one Worker per step ("1 of 7" to "7 of 7"), in this order (owner's Q1 A, 2026-11-02): **the admin API** (`deploy:staging:api`), **the admin invoices Worker** (`deploy:staging:invoices`), **the admin front** (`deploy:staging:front`), **jobs** (`wrangler deploy --env staging`; it bundles its own code), **the admin finance Worker** (`deploy:staging:finance`), **the portal** and **the website**. Every Worker a step binds already exists when it deploys, and the old finance Worker still answers every admin row and still exports `BillingJobs` and `GatewayEvents.issueGatewayAdvance` until step 5, so the split's deploy has no gap. **From M6.5** (owner's Q3 A) the finance step moves back to right after the invoices Worker (admin API, admin invoices, admin finance, admin front, portal, jobs, website): a deploy that adds a finance method jobs calls must deploy finance before jobs. A failed step stops the job, so nothing deploys after a failed Worker. Each deploy script first runs `scripts/check-staging-build.mjs`: a plain `vite build` names the **production** Worker (the top level of `wrangler.jsonc`), so a non-staging build is refused before `wrangler deploy` runs; for the website it checks that the pages carry env.staging's Turnstile key.
5. Health checks (below): jobs right after its deploy (step 4); the admin's once all four admin Workers are new (after step 5); then the portal and the website after theirs. Before the first deploy, the job checks the deploy-check token is set, so a missing token stops it before anything is uploaded.

If a staging deploy stops part-way, re-run it. With the Q1 order every stop leaves a working set: the new front, jobs and finance each bind only Workers that are already new or still answer the old way. (The steps are the workflow's deploy steps "1 of 7" to "7 of 7" in item 4, not the items of this list.)

### Rolling back the fourth admin Worker on staging (owner's Q2 A, 2026-11-02; early check finding 2)
If the split misbehaves on staging, the lead may roll back straight away and tell the owner afterwards (staging only). **Only one order is safe: the admin finance Worker first, then jobs, then the admin front. Leave the admin invoices Worker and the admin API in place.**
1. **Admin finance first** (`techaust-platform-admin-finance-staging`). The old finance version answers every admin row (invoices included) and exports `BillingJobs` and `GatewayEvents` with `issueGatewayAdvance`. While the front and jobs are still new, they keep working against it: the new front sends invoice rows to the invoices Worker and payments rows to the old finance, which answers them; the new jobs calls `ADMIN_GATEWAY` (`processEvent`, `refreshCheckout`, which the old finance has) and the invoices Worker for `ADMIN_JOBS` and `ADMIN_ADVANCE`.
2. **Then jobs** (`techaust-platform-jobs-staging`). The old jobs calls `BillingJobs` and `GatewayEvents.issueGatewayAdvance` on the finance Worker, which only the old finance has. Rolled back before finance, every `care.bill` and `gateway.advance` message would fail against the new finance and end as dead letters ("Needs review" items and the Owner's bell).
3. **Then the admin front** (`techaust-platform-admin-staging`). The old front sends the invoice, statement, report, approval and dashboard rows to `ADMIN_FINANCE`. Rolled back before finance, those rows would answer 404 from the new finance (deny by default).
4. **Leave the admin invoices Worker and the admin API.** Once the three above are old, nothing calls the invoices Worker, so it does no harm; the API's routes did not change in the split.

Each step: Workers & Pages › the Worker › Deployments › the previous version › Rollback, or `pnpm exec wrangler rollback <version-id> --name <worker> -m "<reason>"` from `apps/admin` (or `apps/jobs`). There are no migrations in the split, so the shared D1 needs nothing (a rollback never reverts data). Then run the health checks by hand (`node scripts/staging-health.mjs admin`, `… jobs`) with the deploy-check token. A later deploy from `main` brings all seven back in the Q1 order.

Limit of the step split (A1 5): a step without the token can't read it, but steps share the runner, so a malicious package in a build step could still leave files or `GITHUB_ENV` entries behind for a later step. The stronger form (a separate deploy job that receives the built files and installs only wrangler) is a possible follow-up, not built.

### Health checks after a deploy (A6 8)
`node scripts/staging-health.mjs <app>` asks the Worker's health route through Cloudflare Access with a service token (`CF-Access-Client-Id` and `-Secret` headers), retries for about 30 seconds, and fails the job unless the Worker itself answers: its JSON with `ok: true`, its own `service` name and `env: "staging"`. A redirect to the Access sign-in page or a non-JSON 401/403 from Access counts as a failure. The checks per app: admin `GET /api/v1/health` = 200, a signed-out `GET /api/v1/leads` = the API Worker's JSON 401 (proves the `ADMIN_API` binding), a signed-out `GET /api/v1/dashboard` = the invoices Worker's JSON 401 (proves `ADMIN_INVOICES`; the finance Worker's from M6.1 until the fourth admin Worker) and a signed-out `GET /api/v1/payments` = the finance Worker's JSON 401 (proves `ADMIN_FINANCE`); a 502 fails, portal `GET /api/v1/health`, jobs `GET /healthz`, web `GET /api/geo`.
- **All four apps: on**, with the deploy-check service token `staging-deploy-check` (`CF_ACCESS_DEPLOY_CLIENT_ID`, `CF_ACCESS_DEPLOY_CLIENT_SECRET`; a Service Auth policy on each of the four staging Access apps; owner, 2026-10-30; Part 4 of [access-staging.md](access-staging.md)). Made for 1 year: renew it before it lapses or the deploy fails at the first check. The benchmark token stays for the benchmark only.

**Legal hold (M3.3; no screen or route until M7.4, VERIFY WITH CA/LEGAL):** a client, a contact or a lead is held by setting its `legal_hold` column to 1 in the staging database, for example `wrangler d1 execute DB --remote --env staging --command "UPDATE contacts SET legal_hold = 1 WHERE id = '<contact id>'"` (the owner or the lead runs it; erase and anonymise then answer 409 `legal_hold` until it is set back to 0).

## Production
Nothing is created until Phase 7 (L3), with owner approval per resource. The production blocks of the `wrangler*.jsonc` files hold no D1, queues, R2, Browser Run, service bindings or secrets, and the jobs Worker states an empty cron list (`triggers` would otherwise be inherited from the top level). The one exception is the admin front, whose production block already names its three service bindings (`ADMIN_API`, `ADMIN_FINANCE`, `ADMIN_INVOICES`).

**Phase 7, the order Workers are created in:** a Worker whose service binding names a Worker that does not exist yet fails to deploy (Cloudflare's service-bindings docs, "Deployment"). So production creates **`techaust-platform-admin-invoices` before the admin front, the admin finance Worker and jobs**, which bind it (`ADMIN_INVOICES`; `ADMIN_ADVANCE`; `ADMIN_JOBS` and `ADMIN_ADVANCE`), and the admin API and the admin finance Worker before the front and jobs that bind them. `scripts/check-prod-readiness.mjs` requires a production twin for every staging service binding (same binding name and entrypoint, naming the production Worker).
