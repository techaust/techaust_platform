### B. Core (B1; pure; ≥ 90 % coverage; `paypal.ts` added to `no-floats.test.ts`)

**`packages/core/src/paypal.ts`** (subpath `@techaust/core/paypal`; no `fetch`, no zod):

- **Origins and the live guard:**
  - `PAYPAL_API_ORIGINS = { test: "https://api-m.sandbox.paypal.com", live: "https://api-m.paypal.com" }`;
  - `paypalOriginFor(settingsMode, liveFlag)` returns the origin, or null for a live mode while `liveModeAllowed("live", flag)` is false.
  - PayPal credentials carry no test or live prefix, so the **mode picks the host**, and a live host is never called while the flag is false: zero fetches.
- **Money:**
  - `usdMinorToValue(minor)`: a positive safe integer to `"12.34"`, built with `Math.trunc` and `%`, never a float.
  - `valueToUsdMinor(s)`: `^(0|[1-9]\d{0,12})(\.\d{1,2})?$` padded to 2 decimals; null for a sign, an exponent, 3+ decimals, empty, or anything over 32 characters (the `money.value` pattern).
- **The order request:** `orderRequestOf({checkoutId, amountMinor, documentNumber, documentType, returnUrl, cancelUrl, brandName, now})` returns `{body, requestId: "ord-" + checkoutId}`. The body:
  - `intent: "CAPTURE"`;
  - `purchase_units: [{ reference_id: checkoutId, custom_id: checkoutId, invoice_id: \`${documentNumber}-${checkoutId.slice(-12)}\`, description: "<Invoice|Proforma invoice|Debit note> {number}", amount: {currency_code: "USD", value} }]`;
  - `payment_source.paypal.experience_context`: `{ brand_name, shipping_preference: "NO_SHIPPING", user_action: "PAY_NOW", landing_page: "NO_PREFERENCE", payment_method_preference: "IMMEDIATE_PAYMENT_REQUIRED", return_url, cancel_url }`;
  - bounds: `custom_id` ≤ 255, `invoice_id` ≤ 127, `reference_id` ≤ 256, `brand_name` ≤ 127, description ≤ 127 (beyond 127 is truncated by PayPal);
  - return and cancel URLs: https (http only for localhost), no user, password or fragment; the query only `?pay=paypal`, `?pay=paypal-cancel`, `?via=paypal` or `?via=paypal&cancelled=1`;
  - amount ≥ 1 cent; the maximum is checked by M6.3's `payAmountVerdict` against the setting `overseasOnlineMaxUsdMinor` (L11), not here.
- **Readers** (a whitelist; never payer name, email, address, phone, `payer_id`, `account_id`):
  - `readPayPalOrder(obj)` gives `{id, status, customId, referenceId, invoiceId, currency, amountMinor, payerActionUrl, fundingSource ('paypal'|'card'|'other'), captures: [...]}`.
  - Each capture: `{id, status, reason, amountMinor, currency, feeMinor, netMinor, finalCapture, createdAt, customId, orderId (supplementary_data.related_ids.order_id)}`.
  - `readPayPalCapture(obj)` gives the same capture shape.
- **The judge:** `judgePayPalCapture(checkout, order|null, capture)` returns ok, or one of:
  - `reference_mismatch`: `custom_id` ≠ the checkout id, or the order id ≠ `provider_link_id`;
  - `order_mismatch`: the capture is not this order's;
  - `currency_mismatch`, `amount_mismatch` (capture or order ≠ the checkout);
  - `capture_pending` (with `reason`);
  - `capture_denied` (DECLINED or FAILED);
  - `not_final`: `final_capture` false on a CAPTURE-intent order.
- **Capture errors:** `captureErrorOf(httpStatus, body)` returns one of:
  - `already_captured` (422 issue `ORDER_ALREADY_CAPTURED`);
  - `instrument_declined` (422 `INSTRUMENT_DECLINED`);
  - `not_approved` (422 `ORDER_NOT_APPROVED`);
  - `expired` (404 `RESOURCE_NOT_FOUND`, or an expired issue);
  - `in_progress` (409, 202, or `PREVIOUS_REQUEST_IN_PROGRESS`);
  - `retry` (5xx or network);
  - `refused` (any other 4xx).
  The issue names are UNCONFIRMED; an unknown name is `refused`, which leads to a review item.
- **Webhooks:**
  - `PAYPAL_EVENT_TYPES` map:
    - `CHECKOUT.ORDER.APPROVED` → `checkout.approved` (new `ProviderEventType`);
    - `PAYMENT.CAPTURE.COMPLETED` → `payment.captured`;
    - `.PENDING` → `payment.pending` (new);
    - `.DENIED` / `.DECLINED` → `payment.failed`;
    - `.REFUNDED` → `refund.processed`;
    - `.REVERSED` → `payment.reversed` (new);
    - anything else → `other`.
  - `crc32(bytes)`: IEEE, unsigned decimal; table built at module top level.
  - `payPalSignedMessage(transmissionId, transmissionTime, webhookId, crc)` gives `"<id>|<time>|<webhookId>|<crc>"` (UNCONFIRMED format).
  - `isPayPalCertUrl(u)`: https; host exactly `api.paypal.com` or `api.sandbox.paypal.com`; path starting `/v1/notifications/certs/`; ≤ 500 characters; no user, port, query or fragment. Hosts and path UNCONFIRMED.
  - `verifyPayPalSignature({bytes, headers, webhookId, keyFor})`: `keyFor(certUrl) → Promise<CryptoKey|null>` is injected, so core never fetches. It checks:
    - `PAYPAL-AUTH-ALGO` is exactly `SHA256withRSA`;
    - the signature is base64 of ≤ 500 characters;
    - the transmission id matches `^(?!\d+$)\w+\S+` and is ≤ 50;
    - the time is RFC 3339 and ≤ 100.
    The check itself is `crypto.subtle.verify("RSASSA-PKCS1-v1_5", key, sig, utf8(message))`.
  - `spkiFromCertificate(der)` (only if `X509Certificate` is missing, Step 0.3), `pemToDer`, and `certValidAt(der, now)` (notBefore ≤ now ≤ notAfter).
- **Events:**
  - `parsePayPalEvent(obj)` gives `{id, type, name, orderRef, captureRef, amountMinor, currency, occurredAt}`, or `invalid_event`. The order ref comes from `resource.id` for CHECKOUT.ORDER.* and from `resource.supplementary_data.related_ids.order_id` for PAYMENT.CAPTURE.*.

**The PayPal client: `apps/admin/worker/gateway/paypal.ts`** implements `PaymentProvider`:

The client's rules:
- Every call: the live guard first, then `AbortSignal.timeout(8000)`; only the two `api-m` origins.
- **Token:** `paypal-token.ts`, a per-isolate cache `{origin, clientIdHash, token, expiresAt}`. It is minted with `POST /v1/oauth2/token`: Basic auth of `PAYPAL_CLIENT_ID:PAYPAL_CLIENT_SECRET`, body `grant_type=client_credentials`, form content type. It is kept until `expires_in` minus 300 s. On a 401 the cache is dropped and the call retried once. The token and the secret are never logged.

**`capturePayPalCheckout` (`paypal-capture.ts`).** Callers: the portal return, the `CHECKOUT.ORDER.APPROVED` event, `gateway.refresh` (through `refreshCheckout`) and the staff "Check now". Steps:
1. Read the checkout by `(paypal, order id)`.
   - None: from the return → `not_found`; from an event → `ignored` / `not_ours` (L13).
   - `paid` → `paid`. `capture_pending` → re-fetch the capture (step 4).
   - `expired`, `cancelled` or `failed` **with `capture_started_at` NULL** → `expired` or `not_completed`. **With `capture_started_at` set** (a capture may have gone through before the row ended) → `GET /v2/checkout/orders/{id}` first: a COMPLETED capture goes to step 5's never-drop path (below); no capture → the answer as before.
2. **Claim** (A's claim statement). 0 rows → re-read:
   - a fresh claim held by another call → `processing`;
   - the document no longer payable, or the amount above its balance → checkout `cancelled` (guarded) and `changed`. **Nothing is captured, so no money is taken that couldn't be applied.**
3. `POST /v2/checkout/orders/{id}/capture` with `PayPal-Request-Id: cap-<checkoutId>-<capture_started_at>` (one id per claim: retries within a claim are idempotent, and a new claim after `INSTRUMENT_DECLINED` gets a new id, so PayPal can't replay the stored decline; PayPal keeps keys 6 h, longer than our 3 h 30 min window; an order with intent CAPTURE is captured once whatever the id: re-read at Step 0.4) and `Prefer: return=representation`. Outcomes:
   - `already_captured` → `GET` the order and read its capture;
   - `instrument_declined` → release the claim, answer `declined` with `retryUrl` = the stored `payer-action` URL (PayPal's restart guidance, UNCONFIRMED);
   - `not_approved` → release, `not_completed`;
   - `expired` → checkout `expired`;
   - `in_progress` or `retry` → keep the claim (it goes stale), answer `processing`; the event path answers `retry`. A claimed row is never ended locally (A: every local end is guarded `AND capture_started_at IS NULL`); the sweep re-fetches it instead;
   - `refused` → review `capture_refused`, checkout stays.
4. `judgePayPalCapture` on the capture answer, which counts as the server-to-server proof (ADM-PAY-04). On the event path, the `GET` order or capture is the re-fetch.
5. **COMPLETED and ok:**
   - an export invoice or debit note → **one batch**: the confirmed payment `ppl_<id>`, allocate `min(amount, balance)`, recompute, `ledger_result`, the checkout → `paid` with `provider_capture_id`, other open checkouts → `stale`, the event → processed, audit (actor `contact` from the return, `webhook` from an event, `system` from the sweep, the member from "Check now"), owners' bells. An overpayment becomes credit with an `overpaid` item. T11's `deedDraftStatements` are appended after the recompute, guarded on the audit row, as M6.2 B2 does.
   - a proforma → per Step 0.2c (default: pending with `requested_allocations`, review `advance_blocked` / `fx_rate_needed`, bell).
6. **PENDING** → the checkout moves to `capture_pending` with the capture id; review `capture_pending` (reason: `ECHECK`, `PENDING_REVIEW`, `RECEIVING_PREFERENCE_MANDATES_MANUAL_ACTION`, …); bell; **no payment row** until COMPLETED (L6).
7. **DECLINED or FAILED** → checkout `failed`, review `capture_denied`, bell, no payment.
8. **A mismatch** with the client known and not anonymised → payment `pending_verification` (no ledger move) and a review of the matching kind (M6.2 L7). Anonymised → review `client_gone` only.
9. **Never drop captured money** (M6.2 early check item 3, applied to every PayPal path: return, event, sweep, "Check now"): if step 5's guarded batch changes no row (the checkout ended, the document changed, the balance moved), a second batch records the capture as `pending_verification` with no allocation plus a review item `late_capture` (new kind) and a bell. The checkout keeps its ended status; `provider_capture_id` is set once on it.

**`processPayPalEvent({eventId})`:** not `received` → `duplicate`. Then by type:
- `checkout.approved` → `capturePayPalCheckout`.
- `payment.captured`, `payment.pending`, `payment.failed` → find the checkout by `related_ids.order_id`, re-fetch `GET /v2/payments/captures/{id}`, then steps 5–8.
- `payment.reversed` or `refund.processed` on a confirmed `ppl_` payment → review `reversed_after_confirm` or `refunded_outside` and a bell; **no ledger move** (M6.5). With no payment row → `ignored`.
- `other` → `ignored`.
Network error or 5xx → `retry`.

### D. Jobs Worker (B2)

**`apps/jobs/src/hooks/paypal.ts`, `POST /paypal` only.** Other methods and `/paypal/*` → 404 with no D1. The hook, in order:
1. JSON content type, else 415.
2. A streamed 64 KiB cap on the **bytes**, else 413.
3. `PAYPAL_WEBHOOK_ID` unset → 503 `hook_unconfigured`, nothing written.
4. The five `PAYPAL-*` headers missing or malformed, or `PAYPAL-CERT-URL` not allow-listed → 400 `signature_missing`, **not counted**.
5. The key for the cert URL from a per-isolate cache (≤ 4 entries), with a negative cache of failed URLs (10 minutes) and **at most 2 cert fetches per isolate per minute** (over it → 503 `cert_unavailable`, no fetch, no D1); the path must match `^/v1/notifications/certs/CERT-[A-Za-z0-9-]{1,64}$` (UNCONFIRMED, re-read at Step 0.4). On a miss, `fetch` the allow-listed URL (`AbortSignal.timeout(5000)`, ≤ 16 KiB, PEM), check the validity dates and import the key. A failure → 503 `cert_unavailable` with no D1 (PayPal retries).
6. `verifyPayPalSignature` over the CRC32 of the **raw bytes**. A failure → 400 `signature_invalid`, then `UPDATE hook_failures … WHERE count < 50` (key `paypal:sig:<hour>`) and one owners' bell at 5.
7. Decode UTF-8 and parse.
8. The event id (`payPalEventIdOf`, else the fallback).
9. **Ours or not** (reviewer X3; as M6.3): the event's `resource.custom_id` (a capture) or `resource.purchase_units[0].custom_id` (an order) must be a UUIDv7, else **200 with no D1 write**, no enqueue, one log line (`not_ours`). An unknown type that is ours → row `ignored`, 200. **Exception (re-check N3):** a `PAYMENT.CAPTURE.REFUNDED` or `.REVERSED` event without a `custom_id` but with a capture link (`links[rel=up]` or `supplementary_data.related_ids`) is kept as `received`, and finance sorts it (no row for the capture → `ignored`); re-read at Step 0.4.
10. `INSERT … ON CONFLICT(provider,event_id) DO NOTHING`, then read the status. New or still `received` → `LEADS_QUEUE.send({kind:"gateway.event", eventId})`. Answer 200 `{ok:true}`. A send failure → 500 with the row kept.

Never log the body, signature, certificate or webhook id. **CPU ≤ 5 ms p99** (JOB-HOOK-03): CRC32 over ≤ 64 KiB, one parse, one native RSA verify, 2 D1 statements, 1 send. The cert fetch is wall time, once per isolate.

### Decisions taken (each with its reason)
1. **A refused capture releases the claim** (C step 3: "checkout stays"): the row stays live but unclaimed, so the sweep doesn't refresh a dead claim every 15 minutes; PayPal's own expiry ends it.
