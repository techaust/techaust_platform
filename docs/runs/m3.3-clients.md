### What to build (API and data; no screens)
0. **Bundle limit:** `scripts/check-admin-bundle.mjs` to 75 % of M0 (207,939 bytes), with a comment citing the docs/13 Lead row of 2026-10-25.
1. **Schema** (ADD COLUMN, index and trigger only; `clients` and `contacts` are referenced and are **never rebuilt**):
   - generated: `ALTER TABLE contacts ADD legal_hold integer DEFAULT false NOT NULL`; `CREATE UNIQUE INDEX contacts_one_primary ON contacts(client_id) WHERE is_primary = 1`; `CREATE INDEX clients_created ON clients(created_at, id)`; `CREATE INDEX clients_name_nocase ON clients(display_name COLLATE NOCASE)`; `CREATE INDEX email_log_to ON email_log(to_email, created_at, id)`;
   - custom trigger set `client_triggers` in `triggers.ts`: `clients_currency_locked` (BEFORE UPDATE OF currency, when it changes and an invoice-family document of any status exists); `contacts_anonymised_frozen` (BEFORE UPDATE ON contacts WHEN OLD.anonymised_at IS NOT NULL); `clients_state_check` on INSERT and UPDATE OF gst_status, state_code (registered and unregistered need a current state code, overseas needs NULL; owner Q1);
   - `scripts/portal-sql.mjs` sample clients get `state_code '19'`.
   `pnpm db:generate` leaves no diff; the migration guard passes.
2. **Core `packages/core/src/clients.ts`** (pure, subpath `./clients`, ≥ 90 % coverage): `CLIENT_FINANCE_FIELDS` (the one list of finance fields); `clientTaxCheck({gstStatus,country,gstin,stateCode})` (registered: valid GSTIN, state defaults to the GSTIN's, a different state is a warning `gstin_state_mismatch`, never a block; unregistered: `IN` + a state code; overseas: not `IN`, no GSTIN, no state); `INVOICE_FAMILY`; `ANONYMISED_CONTACT = "Removed contact"`, `ANONYMISED_CLIENT = "Removed client"` (07-J) and `anonymisedEmail(id)` = `anonymised+<id>@invalid`. Shared by convert and the client routes. VERIFY WITH CA/LEGAL.
3. **Shared HTTP helpers `apps/admin/worker/http.ts`** (param, body, query, isUnique, text/optText, STALE_VERSION) used by leads, users, settings, search, notifications (saves bundle).
4. **Routes** (every one a `ROUTES` row; new matrix rows `clients.finance.write {owner, staff}` and `clients.dataErase {owner: "step-up"}`):

   | Route | Action | Audit |
   |---|---|---|
   | GET /clients (keyset 25/50; `q` prefix on code or name; filters gstStatus, currency) | clients.read | none |
   | POST /clients (code `C####`, shared SQL; optional first contact in the same batch) | clients.write | client.create |
   | GET /clients/:id (client, contacts ≤ 100, `currencyLocked`, source lead ref, `updatedAt`) | clients.read | none |
   | PATCH /clients/:id (finance keys → 400; `expectedUpdatedAt` → 409) | clients.write | client.update |
   | PATCH /clients/:id/billing (the finance fields) | clients.finance.write | client.billing_update |

   | GET, POST /clients/:id/contacts | clients.read / clients.write | contact.create |
   | PATCH /contacts/:id | clients.write | contact.update |
   | POST /contacts/:id/export `{part?, after?}` | clients.dataExport | contact.export (one row per call) |
   | POST /contacts/:id/erase `{mode: erase or anonymise, reason}` | clients.dataErase | contact.erase / contact.anonymise |

   One mapper `clientView(row, role)` drops `CLIENT_FINANCE_FIELDS` without `clients.finance.read`; Activity hides `FINANCE_AUDIT_ACTIONS` (add `client.billing_update`) from roles without it; audit summaries hold ids, codes and field names only. **Currency:** conditional write (`… AND NOT EXISTS (invoice-family document)`) → 409 `currency_locked`; the trigger is the backstop and its abort also maps to 409. Reasons (07-J): `requested`, `consent_withdrawn`, `not_needed`, `other`.
5. **Contacts:** email lower-cased (`normaliseEmail`), duplicate at the same client → 409 `email_in_use`; one primary (unset the old one first, in the batch); `canSeeFinance` defaults to `isBilling`; portal access defaults to off; marketing consent `{granted, at, source:"admin"}` with `withdrawnAt` when turned off. **Access off or an email change, in the same batch:** revoke the contact's live `client_sessions` and delete its unused `magic_link_tokens`, both guarded by the audit row (`packages/db/src/contact-access.ts`). The portal already refuses links and sessions without access; its finance routes come in M4.5/M7.1.
6. **Convert carry-ins (`leads.ts`):** `stateCode` (required as in item 1) and `billingContact` (sets `is_billing`, and `can_see_finance` by default).
7. **Export:** the call without `part` returns the contact, the client (full row for an individual client, else code and name), its suppression entry and a manifest; each further call returns one page (≤ 50 rows, keyset) of one part: `leads` (same email; `client_id` null or this client), `lead_activities`, `sessions` (no token hash), `magic_links` (times only), `acceptances`, `documents` (frozen, recipient email = contact, or any frozen document of an individual client), `email_log` (by address), `audit_log` (actor = contact, entity = contact), `access_log` (actor = contact). The browser assembles the file. Anonymised contact → 409.
8. **Erase and anonymise: one `mutate` batch, audit-first.** The audit row is inserted only while the contact is live, no legal hold on the contact, its client or any matched lead, and (erase only) `NOT CONTACT_ON_ISSUED_DOCUMENT_SQL` (exported from `packages/db`: an acceptance, a frozen document whose recipient email matches, or an individual client with any frozen document). Every following statement is guarded on that row: matched leads' activity bodies → NULL and bell rows deleted; leads' name, email, phone, company, message, call window, UTM, source page, referrer and next-action note anonymised, consent `ipHash` removed; sessions and tokens deleted; the contact anonymised (`ANONYMISED_CONTACT`, `anonymisedEmail`, other fields and flags cleared, `anonymised_at`) or deleted (erase); an individual client's record anonymised (`ANONYMISED_CLIENT`, addresses, notes and tags cleared) when this was its last live contact (owner Q2). **Kept** (owner Q3): issued-document snapshots, acceptances, `audit_log`, `access_log`, `email_log`, `email_suppressions`, `auth_attempts`. The erase row is written on entity `client` (its summary carries the contact id). When nothing is written, re-read only to choose 404, 409 `legal_hold` or 409 `on_issued_document`. VERIFY WITH CA/LEGAL.
9. **Search:** clients by code and name prefix, contacts by email prefix, on indexes, for `clients.read`.

### Rules
CLAUDE.md conventions (keyset ≤ 50, index every filter, zod/mini, subpath imports); no personal data in logs or audit rows; existing tests change only on purpose (name each); heavy commands via `bash tools/heavy.sh --log <name> …`; commit every 20 minutes; whole-repo lint once at the end.

### Tests (critical)
- **Sales and finance:** RBAC loops (every finance route 403 for Sales); deep-scan every client, contact, search and activity response for Sales for `CLIENT_FINANCE_FIELDS`; one test ties the list to the billing schema keys, the mapper and the DB columns; Sales activity has no finance actions.
- **Erase blocked:** a frozen document with the contact's email, an acceptance, or an individual client with a frozen document → erase 409 and nothing written (row counts incl. audit); anonymise succeeds there; a document frozen between the read and the batch (D1 proxy) still blocks.
- **Legal hold** on client, contact or a matched lead → 409 for both modes.
- **Currency:** a draft invoice → 409; a raw UPDATE refused by the trigger; a proposal alone doesn't lock; an invoice inserted mid-request → 409.
- **State check:** unregistered `IN` without a state refused (API and trigger); overseas with a state refused.
- **Scoping:** the same email at clients A and B: erasing at A leaves B's contact, sessions, tokens and B-linked lead untouched; an export at A has no B rows; `clientId` in a body → 400.
- **Portal:** access off or email change → sessions revoked and tokens deleted; access back on → old sessions stay revoked; anonymise or erase → sessions and tokens gone.
- **Other:** atomicity (a failing trigger aborts the whole erase); export needs step-up, one audit row per call, page bounds; audit hygiene scan; EXPLAIN plans for list, search, activity and export; migration list; triggers installed.
