### Contracts (builder)

**A. Magic-link request: `POST /api/v1/auth/magic {email}` (public) [POR-01]**
- zod/mini schema; email trimmed and lower-cased exactly like `inviteFinishRequest`.
- Batch 1: (1) `RESERVE` on `p:req:<HMAC(PORTAL_KEY_PEPPER, "req:"‖IP)>` (10/hour/IP, lock 1 h); (2) `RESERVE` on `p:mail:<HMAC(pepper, "mail:"‖email)>` (3/15 min, lock 15 min), skipped in SQL while the IP key is over (the M1.5 `?6` pattern); (3) contact read `SELECT c.id, cl.display_name FROM contacts c JOIN clients cl ON cl.id = c.client_id WHERE c.email = ?1 AND c.portal_access = 1 AND c.anonymised_at IS NULL` (uses `contacts_email`).
- Either limit reached: 429 `rate_limited` with `Retry-After`; identical for known and unknown emails (every email is counted); nothing else written.
- Otherwise batch 2: one `magic_link_tokens` row per eligible contact (32 random bytes base64url, SHA-256 at rest, `expires_at = now + 15 min`, `request_ip` NULL), then the access row (actor NULL; it is a sign-in event under Q1 = A). Unknown/ineligible email: batch 2 is only the access row.
- Reply always `200 {ok:true}`: same status, body (apart from `request_id`) and D1 call count (2) for known and unknown emails. Not constant time; not verified on real D1.
- Links go to a `MagicLinkSender` (`apps/portal/worker/sender.ts`, `send(links: {to, orgName, url}[])`). **M1.6 ships no implementation that sends or logs anything**; tests inject a capturing sender; M2.4 plugs in the email queue. Link format `origin + "/auth/callback#t=" + token`. One email at several organisations → one link per organisation (Q3).

**B. Verify: `POST /api/v1/auth/magic/verify {token}` (public) [POR-01, POR-02]**
- Malformed token (not 43 base64url chars) is a failure: same body, counted.
- Batch 1 (one call): (1) IP block read on `p:fail:<HMAC(pepper, "fail:"‖IP)>`; (2) `UPDATE magic_link_tokens SET used_at = ?now WHERE token_hash = ?1 AND used_at IS NULL AND expires_at > ?now AND NOT EXISTS (<fail key locked>)`; (3) `INSERT INTO client_sessions … SELECT ?sid, c.id, c.client_id, … FROM magic_link_tokens t JOIN contacts c ON c.id = t.contact_id JOIN clients cl ON cl.id = c.client_id WHERE t.token_hash = ?1 AND t.used_at = ?now AND c.portal_access = 1 AND c.anonymised_at IS NULL`; (4) audit `portal.login` (actor_type `contact`) guarded on the session row (new `{ clientSessionId }` guard, G); (5) access row (200), same guard.
- Session created: 200 `{ok:true}` + `Set-Cookie: __Host-ta_portal=<token>; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=7776000`.
- Not created: 401 `link_invalid` ("This link has expired or was already used. Request a new link."), same body for expired, used, unknown, malformed, or a contact that lost access (that token stays used); +1 call: `FAIL_SQL` on `p:fail:` (20 failures/hour → 15-minute block) + the access row 401 (a sign-in event).
- IP blocked: 429 in one call; nothing written; the token is **not** used.
- Two parallel verifies of one token → exactly one session (atomic `UPDATE … used_at IS NULL`).

**C. Session guard and route table [POR-02, POR-03]**
- `apps/portal/worker/guard.ts`: table-driven `ROUTES` like admin; access `public` | `session` | `finance`; no row → 404; matched with `routePath(c, -1)`.
- No `__Host-ta_portal` cookie → 401 `unauthenticated`, **no D1 call** and no access row (Q1 = A).
- `SESSION_READ` (one call): `client_sessions s JOIN contacts c ON c.id = s.contact_id AND c.client_id = s.client_id JOIN clients cl ON cl.id = s.client_id WHERE s.id = ?1 AND c.portal_access = 1 AND c.anonymised_at IS NULL`, plus `checkSession`. Losing portal access, being anonymised or moved to another client ends the session at once, with no write. A bad/expired cookie → 401, one call, no access row (Q1 = A).
- Touch at most every 15 min: `idle_expires_at = min(now + 30 d, abs_expires_at)`, riding in the request's access write.
- `finance` routes for a contact without `can_see_finance` → **404** (no route uses it yet; the scope test proves it).
- Every `/api/*` response `Cache-Control: no-store`; CSRF as admin (G); body limit 16 KB; request ID from `cf-ray`.

**D. Scoping helper [POR-03]: `apps/portal/worker/scope.ts`**
- Opaque `ClientScope` `{contactId, clientId, canSeeFinance, sessionId}`; only the guard makes one (constructor not exported); `scope(c)` throws if a route reaches it without a session.
- `forClient(db, scope, sql, ...params)` binds `?1 = scope.clientId` and throws if `sql` lacks `client_id = ?1` (or `.client_id = ?1`). Not yours = `notFound(c)`, same body as a missing id. `requireFinance(scope)`.
- Tables without `client_id` (`milestones`, `document_lines`…) are reached only through a join to a scoped parent; write that rule in the file header for M4.5/M7.1.

**E. Own-session routes**
- `GET /api/v1/me` (`session`): `{contact:{name,email}, organisation:{displayName}, canSeeFinance}`.
- `POST /api/v1/auth/logout` (public): with a cookie, one batch (revoke where `revoked_at IS NULL`, audit `portal.logout` guarded on `changes()`, access row) and clear the cookie; without a cookie: 204, cookie cleared, no D1.
- `POST /api/v1/auth/sessions/revoke-all` (`session`): revoke every live session **of this contact only**, audit `portal.sessions_revoke_all`, access row, clear the cookie. No session list.

**F. Single-document tokens [POR-06, library + one route]**
- `packages/auth/src/portal.ts`: `newDocToken()` (32 bytes, SHA-256 at rest) and `docTokenStmt(db, {documentId, purpose: "view_pay", expiresAt})` → `{token, stmt}` for a caller's batch (M5/M6 send flows).
- `POST /api/v1/t/document {token}` (public). The token travels only in the body; the link form is `portal…/t#<token>`; no route has a token in its path or query.
  - Read batch: IP block read, then `doc_access_tokens t JOIN documents d` where not revoked or expired, purpose matches, `d.voided_at IS NULL`, `d.status NOT IN ('draft','pending_approval','void')`, `d.type IN (<VIEW_PAY_TYPES>)`; `VIEW_PAY_TYPES` = `proforma`, `tax_invoice`, `export_invoice` (lead confirms in M5).
  - Valid: 200 `{document:{id,type,number_display,status}}`, then one batch: audit `doc_token.use` (actor_type `contact`, actor NULL, entity the document) + access row.
  - Invalid: 404 `not_found` + `FAIL_SQL p:fail:` + access row (a document-link use is a sign-in event under Q1 = A). IP blocked: 429, nothing written.
- No schema change to `doc_access_tokens`.

### Tests (named with PRD IDs; failure paths included)
**POR-01**
- Unknown email, contact without portal access, anonymised contact, an email at two organisations, and a valid contact: same status, body (ignoring `request_id`) and D1 calls; tokens only for eligible contacts, one per organisation; the sender captures exactly those.
- The raw token appears in no text column of any table (scan every table); only the SHA-256 is stored.
- Expiry: works at 14:59, refused at 15:01. Single use: second verify → 401, same body.
- Two parallel verifies (`barrierDb`): one 200, one 401, one session, one `portal.login`.
- Quotas: 4th request for one email in 15 min → 429 (unknown email too); 11th from one IP in an hour → 429; a refused request writes nothing (row counts before/after); window rollover.
- `RESERVE_SQL` agrees with `reserveAttempt` on M1.4's 8 hand-written and 40 seeded sequences, with the new window/lock parameters; admin's defaults unchanged.
- 20 failed verifies → 15-minute block → 429 even with a valid token; the valid token is not used up; nothing written.
- A contact who loses access after the link was issued → 401, the token is used, no session.
- Email matched trimmed and case-insensitively. No route has a token in its path or query (route-table test); the CLI's link builder puts the token after `#t=`.

**POR-02**
- Cookie attributes exactly as in B; no `Domain`.
- Idle and absolute expiry: 30 days idle → 401, just under → OK; 90 days → 401 even with activity. Touch at most every 15 min (D1 calls). New session id per sign-in.
- Sign out: cookie cleared, old cookie → 401. Sign out of all devices revokes only this contact's sessions (another contact of the same client and client B keep theirs).
- Triggers abort clearing `revoked_at` or changing `contact_id`/`client_id`.
- Realm separation: a valid staff token sent as `__Host-ta_portal` → portal 401; a valid portal token as `__Host-ta_admin` → admin 401 (`realm.test.ts`).

**POR-03**
- Scope only from the session; a `client_id`/`contact_id` in query, body or headers is ignored (test-only echo route via `createApp({ testRoutes })`).
- `forClient` throws on SQL without `client_id = ?1`.
- SQL spy: every session route as client A; every statement touching a table with a `client_id` column binds A's id, apart from a named allow-list containing only the guard read; the table list comes from `pragma_table_info`.
- Cross-tenant harness `crossTenant(ROUTES, fixtures)` (reused by M4.5/M7.1), run here on test-only routes: B's document id → 404 with the same body as a random id; a draft → 404; a finance route for a non-finance contact → 404.
- Changing the contact's `client_id`, turning portal access off or anonymising → 401 on the next request. `GET me` returns only the session's contact and organisation. Portal Worker SQL never names a `staff_` table (source scan).

**POR-06 (tokens)**
- 32 bytes, stored hashed, resolves exactly one document; response holds only that document's header.
- Revoked, expired, draft, pending approval, void, wrong purpose and wrong type → 404, same body. Every valid use writes exactly one `doc_token.use` row. Invalid tokens count toward `p:fail:`; a blocked address writes nothing.

**Logs and the rest**
- Audit: login, logout, revoke-all and token use each write exactly one audit row (actor_type `contact`, `request_id`, ip, ua); failures write none.
- NFR-9 (Q1 = A): access rows for every signed-in request and every sign-in event (magic request, verify ok/fail, document-link use, logout), realm `portal`, route pattern, actor = contact id after sign-in, NULL before; **no access row** for no-cookie/bad-cookie 401s, CSRF 403/415 or unknown routes (tests assert both directions).
