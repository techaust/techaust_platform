- **O-Q1:** lines not from the catalogue are ignored by the 10 % guard on both sides (rule A). They're listed on the approval screen.

## Lead decisions proposed by the analyst (for docs/13 once accepted)
1. **One document code path for both types** (ADM-EST-01). The routes live under `/v1/documents` and take `type: "proposal" | "estimate"`.
2. **Versions:**
   - `version_group_id` = v1's id.
   - At most one open draft per group.
   - A new version is made only from the latest frozen version, and never once any version of the group is accepted.
   - v1 takes the next number of its series at its first send. v2 and later keep v1's `series`, `fy`, `number` and `number_display`, even across a 1 April. The counter doesn't move.
3. **Approval is a record, not a status** (the 2026-10-07 decision). `status` stays `draft` while an approval is pending, and GET returns a derived `approval.state`.
4. **`content_sha256`** = SHA-256 of the canonical draft content, ids left out. It covers:
   - the document fields, lines, sections and schedule;
   - the supply type and place of supply;
   - every total.

   Every save writes it. A save that changes it expires every pending or approved discount approval in the same batch. **An expired approval never revives,** even if the content is reverted.
5. **The catalogue reference is server-only.** `catalogue_rate_minor` is copied from the catalogue when a line is added: the default-line rate, else the headline price, in the document's currency. It is never accepted from a request. It is kept across saves and revisions.
6. **Catalogue lines keep the catalogue's SAC and GST rate.** Custom lines set their own, subject to `allowLineOverride`.
7. **Saves send parts.** `PATCH` carries any of `fields`, `lines`, `sections` and `schedule`. The server reads the other parts, rebuilds the whole content, recomputes it, hashes it, and writes only the parts that were sent. This keeps D1 row writes within the free budget (risk notes).
8. **Send in M4.3 does the database work only:** freeze, number, `sent`, lead stage. Email is M4.5's and the PDF is M4.4's, both through `afterSend`. Until M4.5 merges, the staging screen says so honestly (copy 07-O).
9. **Terms:** a draft pins the newest proposal terms version when it is created. A newer version raises the warning `terms_outdated`. Send is refused while no proposal terms version exists (`terms_missing`).
10. **Schedules are percent mode only in M4.3.** Amount mode is a follow-up.
11. **Approval notifications are in-app only in M4.3** (`notifications`, the bell). The two 07 §8 emails come with M4.5's email work. Alternative: M4.3 queues them like staff alerts, which adds the jobs consumer and two templates.
12. **Sections:**
    - Kinds: `cover`, `summary`, `problem_goals`, `scope`, `deliverables`, `timeline`, `team`, `how_we_work`, `estimate`, `assumptions_exclusions`, `terms`, `acceptance`, plus up to 3 `custom`.
    - `estimate`, `terms` and `acceptance` appear exactly once and can't be hidden, but can be reordered (ADM-PROP-02).
    - Bodies use the notes Markdown subset (`packages/core/src/markdown.ts`), parsed only in browsers, the portal and the PDF, never in the admin Worker.
    - Caps: ≤ 16 sections, ≤ 6,000 characters each, ≤ 30,000 in total.
13. The `document` body kind is **96 KB**, on `PATCH /documents/:id` only. Everything else stays at 16 or 32 KB.

### 4. Item 9: the expiry job
- **Where:** `packages/core/src/expiry.ts` (new, no zod, subpath `@techaust/core/expiry`: `ExpireMessage`, `expireMessage(scheduledTime)`, `isExpireKind`, `isExpireMessage`, `EXPIRE_PAGE` = 50), `apps/jobs/src/expire.ts` (new), `queue.ts`, `stats.ts`, `index.ts`.
- **Cron:** `enqueueStats(env, scheduledTime, also = [])` puts the one `{kind: "documents.expire", asOf: <IST date of the run>}` message into its existing `LEADS_QUEUE.sendBatch`; `scheduled` passes it. The cron reads no D1 for it (a test runs `enqueueStats` with a database that rejects every call). `asOf` is the IST date of `scheduledTime` (22:00 UTC is 03:30 IST of the next day), so a `valid_until` of yesterday is due and `valid_until = today` is **not** expired.
- **Consumer `processExpire`:** one page per message. A pick (`SELECT id … INDEXED BY documents_status_valid_until WHERE status IN ('sent','viewed') AND type IN ('proposal','estimate') AND valid_until < asOf AND id > after ORDER BY id LIMIT 50`), then ONE `db.batch`: the audit insert (`INSERT … SELECT` from `json_each`, `CROSS JOIN documents`, conditions repeated, system actor, summary = `documentId, type, version, number, validUntil, asOf`, no title or text) **first**, then the `UPDATE … FROM json_each` to `expired`, conditions repeated. Audit first means each audit row is for a document that was still due in that same transaction. Exactly 50 picked → a continuation `{…, after: <last id>}` sent after the page is written. A rerun or a redelivery picks nothing.
- **Queue:** `isExpireKind` is routed after the statistics routing and before the lead fall-through; a malformed expiry body is acknowledged and logged (`documents.expire_unknown`), never a lead; a dead-lettered one is acknowledged and logged with no alert (`documents.expire_dead_letter`); a database error is retried like any other. The cron comment in `index.ts` is updated.
- **EXPLAIN:** the pick is a `SEARCH documents USING INDEX documents_status_valid_until (status=? AND valid_until<?)`; the audit and the update find each document by its id (the update has a unary plus on its repeated conditions, because without it the planner walked the whole due set through the status index and probed the id list for each row).
- **Tests** (`apps/jobs/test/expire.test.ts`, 17; `core/test/expiry.test.ts`, 4): the cron message and date across a month, a year and the 18:30 UTC edge; no D1 read; `valid_until` yesterday / today / later / null; viewed and estimates; drafts, accepted, rejected, revised, expired and a `proforma` untouched; the frozen-document trigger lets `status` change and nothing else of the row changes; one audit row per document (keys, system actor, no title); idempotent rerun; a document accepted between the pick and the batch is left alone with no audit row (a proxy runs the accept before the batch); 51 due → 50 + continuation, then 1; exactly 50 → a continuation that finds nothing; queue routing, malformed bodies, dead letters, a retry on a database error; the three EXPLAIN checks.
