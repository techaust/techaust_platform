### Contracts (builder)

**A. Lockout reservation (LD1; fixes the M1.4 pre-read finding)**
- `packages/auth/src/lockout.ts`: pure `reserveAttempt(a, nowMs, lockAfter = LOCK_AFTER)`. Returns `{allowed:false, row:a}` when `a.lockedUntil > now`; otherwise `{allowed:true, row, lockStarted}`, where `row` follows exactly what `recordFailure` does.
- `apps/admin/worker/auth.ts` exports `RESERVE_SQL`, replacing `FAIL_SQL` for `acct:` and `code:`: `FAIL_SQL` (`auth.ts:88-94`) plus `… ON CONFLICT(key) DO UPDATE SET <the three CASEs> WHERE locked_until IS NULL OR locked_until <= ?2 RETURNING failures, locked_until`.
  - No row returned = locked: 429, nothing counted.
  - A row returned = counted; go on to verify, even when this reservation set the lock.
- Keys: `acct:<32-hex SHA-256(email)>` for passwords on `/login`; `code:<user id>` for codes on `/totp`, `/recovery` and step-up. A full sign-in deletes both; a successful step-up deletes `code:` only.
- `/login`: one batch `[ip lock read, RESERVE acct (skipped if the IP is locked), user read]`; the `isLocked` pre-read (`auth.ts:201`) goes. A wrong password causes no further counter write.
- `/totp`: one batch `[ip lock read, RESERVE code:<claim.sub>, TOTP_READ without the attempts join]`; the check at `auth.ts:232` goes.
- `/login` keeps putting `ak` in the challenge so the success batch can delete `acct:`. Challenges issued before the deploy must keep working.
- When a lock starts on a real account, write one `alert.lockout` audit row (+1 D1 call, rare). Unknown emails get no alert.

**A2. Per-IP counter (LD2)**
- Key `ip:<32 hex of HMAC(SALT_PEPPER, "ip:"‖CF-Connecting-IP)>`: no new secret, no raw IP stored.
- Counts failures only. 100 failures per hour → 15-minute IP block (50 would lock the benchmark runner). A request from a locked IP writes nothing.
- No Rate Limiting binding (hosted change; not this task).

**B. Session guard and RBAC (LD6)**
- New `apps/admin/worker/guard.ts`. `requireSession`: one read (the existing `/me` join plus `u.totp_enabled_at IS NOT NULL` and `s.step_up_until`); sets `c.var.user = {id, role, sessionId, stepUpUntil}`. The 15-minute touch shares the call with the access-log insert.
- Routes are table-driven: method, pattern, access (`public` | an `Action`), audit action. The guard finds the row via `routePath(c)` from `hono/route` (verify it inside the basePath sub-app) and applies `decide(role, action)`:
  - `deny` → 403 `forbidden`; `step-up` without `stepUpUntil > now` → 403 `step_up_required`; `approval` → the handler decides; no row → 404 (deny by default at runtime).
- New matrix actions in `packages/core/src/permissions.ts`: `users.read` {owner}, `account.own` {all roles}, `account.recoveryCodes` {all roles, step-up}. Update 04 §9 after the merge.
- Every `/api/*` response: `Cache-Control: no-store`.
- **CSRF (LD8):** replace `hono/csrf()` (`index.ts:11`; it checks only form bodies) with the 05 §7.1 middleware: unsafe methods need `Origin` = the app origin, or no `Origin` with `Sec-Fetch-Site: same-origin`; a request with a body must be `application/json`.
- **Request ID (LD7):** `cf-ray`, else 16 random hex characters; every error body carries `request_id`.

**C. Step-up (LD5)**
- `POST /api/v1/auth/step-up {code}` (`account.own`). Batch 1: reserve `code:<uid>`, read the user. Batch 2: replay-guard UPDATE of `totp_last_step`; `UPDATE staff_sessions SET step_up_until = now + STEP_UP_MS` guarded on it; delete `code:`; audit `auth.step_up`; access row.
- `STEP_UP_MS = 10 min` in `packages/auth/src/session.ts`. No recovery codes for step-up. No session rotation.

**D. Recovery codes**
- New `packages/auth/src/recovery.ts`: `newRecoveryCodes()` (10 codes, 16 base32 characters), `normaliseRecoveryCode` (uppercase, strip spaces and `-`), `recoveryCodeHash` (SHA-256 hex).
- `invite/totp` writes the 10 hashes in its activation batch and returns `recoveryCodes` once.
- `POST /api/v1/auth/recovery {challenge, code}`: batch `UPDATE staff_recovery_codes SET used_at = ? WHERE user_id = ? AND code_hash = ? AND used_at IS NULL`, then the session insert guarded on it; then audit, `alert.2fa_change`, delete `acct:` and `code:`.
- `POST /api/v1/auth/recovery/regenerate` (`account.recoveryCodes`, step-up): delete old, insert 10 new, audit, `alert.2fa_change`.

**E. Sessions (LD3, LD5)**
- `GET /api/v1/auth/sessions`: own live sessions `{id, created_at, last_seen_at, ip, user_agent, current}` (id = the token's SHA-256, not a credential).
- `DELETE /api/v1/auth/sessions/:id`, scoped by `user_id`; 0 rows → 404.
- `POST /api/v1/auth/sessions/revoke-all`: everywhere, this one included; clears the cookie.
- Every sign-in creates a new session. Role change, deactivation or 2FA reset revokes all of the target's sessions.
- Known devices: `__Host-ta_device` cookie (32 random bytes; HttpOnly, Secure, SameSite=Strict, Path=/, Max-Age 34560000) + table `staff_known_devices`; set/read at `/totp` and `/recovery`. No alert for the device used at enrolment.

**F. Users (owner; Q1, LD11, LD12)**
- `GET /api/v1/users`, `GET /api/v1/users/invites` (`users.read`).
- `POST /api/v1/users/invites {email, role}` (`users.manage`, step-up): returns `{link: origin + "/invite#t=" + token}` once (stands in for the email until M2.4); the same batch expires older pending invites for that email; an existing user's email → 409 `user_exists`.
- `POST /api/v1/users/invites/:tokenHash/revoke`: sets `expires_at = now`; never deletes.
- `PATCH /api/v1/users/:id {role}`, `POST /api/v1/users/:id/deactivate`, `POST /api/v1/users/:id/reset-2fa` (active users only, never yourself), `POST /api/v1/users/sessions/revoke-all`. All `users.manage`.
- Reset, one batch: user → `invited`, clear `pw_*`, `totp_*` and recovery codes; revoke sessions; insert the invite; audit + `alert.2fa_change`.
- Last-owner guard: SQL condition `… AND (role <> 'owner' OR (SELECT count(*) …) > 1)` → 409 `last_owner`, backed by the LD9 trigger.
- The invitee types their own name at acceptance (`inviteFinishRequest` gains `name`; no schema change).
- Break-glass `pnpm admin:reset-2fa` (`scripts/reset-2fa.mjs`, 08 §3.2) on top of the reset path; the owner runs it locally with their own `wrangler login`.

**G. Audit and access writers (reused by the portal in M1.6; Q2)**
- New `packages/db/src/log.ts`: `auditStmt(db, entry, guardSessionId?)` and `accessStmt(db, entry)` return prepared statements for the caller's batch; `entry` carries `requestId`, `ip`, `ua`, `role`.
- `access_log` rows (Q2): every API request by a signed-in staff member, every sign-in attempt, every refusal. `route` is the pattern, never the raw path; `actor_id` null before sign-in; never the email.
- Pure `auditSummary(before, after, sensitive)` in `packages/core` (changed fields; sensitive → `"[masked]"`); in the core index; coverage ≥ 90 %.
- In `startSession`, replace the `changes()` chain (`auth.ts:146`, `:151`, `:157`) with `EXISTS (SELECT 1 FROM staff_sessions WHERE id = ?sid)` guards. Use `changes()` only right after the statement it guards.
- Alerts are stubbed as audit rows (LD4): `alert.new_device`, `alert.2fa_change`, `alert.lockout`, summary `{ua, country, city}`. M2.4 sends the emails.

### Tests (named with PRD IDs; failure paths included)
- **ADM-AUTH-01:** no session → every guarded route 401; an invited user (no TOTP) never gets a session; after a 2FA reset old cookies 401.
- **ADM-AUTH-02 (enumeration):** `/salt`, `/login`, `/recovery` give the same status, body (ignoring `request_id`) and D1 calls for unknown, **invited**, **deactivated** and wrong-password.
- **ADM-AUTH-03:** browser-only (the server never sees the password): the designer's tests cover the 12-character rule, the strength score ≥ 3, the HIBP hit message, and that a failed HIBP lookup doesn't block.
- **ADM-AUTH-04:** TOTP replay refused; 10 codes at enrolment, never returned again; no plaintext code in the DB; a used code refused; **two concurrent uses of one recovery code give one session**; lower case, spaces and hyphens accepted; regenerate needs step-up and kills the old codes.
- **ADM-AUTH-05:** idle, absolute and revoked expiry; touch at most every 15 min; new session id per sign-in; role change/deactivation/reset revoke the target's sessions; sign out everywhere; deleting someone else's session → 404; cookie attributes (session and device).
- **ADM-AUTH-06:**
  - 10 wrong passwords → `/login` 429; 10 wrong codes → `/totp`, `/recovery`, step-up 429 even with the right code; 15-minute lock, then one verified attempt, then locked again; success clears `acct:` and `code:` but not `ip:`; the IP threshold.
  - `RESERVE_SQL` agrees with `reserveAttempt` on M1.4's 8 hand-written and 40 seeded sequences, plus "locked → no row, no write".
  - **Pre-read lock fix:** 9 failures seeded, then 5 parallel wrong `/login` via `barrierDb` → exactly 1×401, 4×429, `failures = 10`, locked; same for `/totp`. **Run against `auth.ts` at 931af75 and paste the failing assertion.**

  - **Concurrent same-code `/totp`** (2 requests) → one 200 + one 401 with the same body; one session; one `auth.login` row; no counter row left.
  - **Locked `/totp` = 1 D1 call (+L).**
