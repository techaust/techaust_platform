## Owner's answers (2026-10-25; docs/13)
- Hours count over the **billing period** (billing day to the day before the next).
- **Q1:** a price or hours change takes effect **from the next billing period**.
- **Q2:** only **billable** time uses the included hours; non-billable time is shown separately.
- **Q3:** **this month's hours are used first**; only the previous period's own unused hours carry over, and they never compound.
- **Q4:** the first, partial period gets the **full** monthly hours.
- **Q5:** a plan paused on its billing day gets **no** hours that period; time logged after a resume in that period is all overage.
- **Q6:** Staff may set any terms **at creation**; later price changes are the owner's.
- **Q7** (VERIFY WITH CA/LEGAL): erasing or anonymising an individual client's last contact also **clears the notes of time entries** on its projects and care plans (minutes and dates stay).

## Lead decisions (from the analyst's draft; docs/13)
1. **History tables.** Two append-only tables, `care_plan_terms` and `care_plan_status_log`. The `care_plans` columns mirror the newest row, guarded by triggers. Readers of a past period (and M5.4) use the history tables, never the mirror.
2. **Fixed fields.** A plan's client, currency, billing day and start date never change; to change one, cancel the plan and create a new one. There is no care-plan delete in M3.5.
3. **Status permissions.** Owner and Staff can pause and resume. Only the owner can cancel (`carePlans.changePrice`), because it can't be undone. A status change takes effect today (IST), or on the start date if that is later.
4. **When time is refused.** Time is refused when the plan isn't active on the work date; entries dated before a pause are still accepted. It is also refused before the start date and on cancelled projects.
5. **Time lock.** The 7-day lock counts from `created_at`, written by the app; `locked_at` stays unused.
   - Dates more than 7 days back are owner-only.
   - No future dates, for anyone.
   - An entry's `user_id` never changes.
6. **15-minute steps.** Included minutes go in 15-minute steps, so the M5.4 overage quantity is exact.
7. **Dashboard tiles by role** follow the docs/04 §9 Reports row:
   - Staff: the delivery tiles plus "my time".
   - Sales: pipeline only.
   - Accountant: finance only.
   - Recent activity uses exact action lists per role, with no summary, IP or user agent.
8. **Live figures.** The dashboard figures are live, from one indexed batch. `stats_daily` is the nightly history (docs/05 §1.2 rule 7 edited).
9. **New matrix rows.** `dashboard.read` and `time.read` (docs/04 §9 edited). `care_plan.terms` joins `FINANCE_AUDIT_ACTIONS`.
10. **Arrives later:** pipeline value with M4.3; the finance tiles with M5 and M6; "Add overage to next invoice" with M5.4; the Workers/D1 usage tile with M7.5.

### What to build (data, logic, API; no screens)
**1. Schema.** One generated migration plus the custom set `time_triggers`: new tables, indexes and triggers only; no ALTER or rebuild of an existing table. Drizzle numbers them by the base. At integration they are deleted and regenerated in merge order, so don't hand-number them.
- **`care_plan_terms`** (append-only):
  - `id` (UUIDv7) and `care_plan_id` (→ care_plans)
  - `effective_from`: text, `date(x) = x`
  - `tier`: one of the care tiers
  - `price_minor` ≥ 0
  - `included_minutes` ≥ 0 and a multiple of 15
  - `ai_ops_minor`: null or ≥ 0
  - `overage_rate_minor`: null or ≥ 0, minor units per hour
  - `rollover`: one of the rollover rules
  - `created_by` (→ staff_users) and `created_at`
  - index `care_plan_terms_plan (care_plan_id, effective_from, created_at, id)`
- **`care_plan_status_log`** (append-only):
  - `id`, `care_plan_id`
  - `status`: one of the care statuses
  - `effective_on`: text date
  - `created_by`, `created_at`
  - index `(care_plan_id, effective_on, created_at, id)`
- **`stats_daily`:**
  - `date`: text, `date(x) = x`
  - `metric`
  - `dimension`: not null, default `''`
  - `value`: `typeof(value) = 'integer'`
  - `updated_at`
  - PRIMARY KEY `(date, metric, dimension)`, plus index `stats_daily_metric (metric, date)`
- **Indexes:** `time_logs_date (work_date, id)`, `care_plans_created (created_at, id)`, `care_plans_status_created (status, created_at, id)`.
- **Triggers** (`time_triggers` in `triggers.ts` with its `TRIGGER_SETS` entry). Each abort message starts with the trigger's name, so the API can map it.
  - `time_logs_one_target_insert` / `_update` (`OF project_id, care_plan_id`): exactly one of project or care plan.
  - `time_logs_day_cap_insert` / `_update` (`OF user_id, work_date, minutes`): `(SELECT coalesce(sum(minutes),0) FROM time_logs WHERE user_id = NEW.user_id AND work_date = NEW.work_date AND id IS NOT NEW.id) + NEW.minutes > 1440` aborts.
  - `time_logs_date_valid_insert` / `_update`: aborts when `date(NEW.work_date) IS NOT NEW.work_date`.
  - `time_logs_plan_active_insert` / `_update` (`OF care_plan_id, work_date`): the plan's newest status row with `effective_on <= NEW.work_date` (`effective_on DESC, created_at DESC, id DESC`) must be `'active'`. No row (before the start) also aborts.
  - `time_logs_project_open_insert`, and `_update WHEN NEW.project_id IS NOT OLD.project_id`: the project isn't `cancelled`.
  - `time_logs_user_fixed`: `user_id` never changes.
  - `care_plan_terms_no_update` / `_no_delete` and `care_plan_status_log_no_update` / `_no_delete`.
  - `care_plans_fixed`: `client_id`, `currency`, `billing_day` and `start_date` never change.
  - `care_plans_terms_match` (BEFORE UPDATE OF tier, price_minor, included_minutes, ai_ops_minor, overage_rate_minor, rollover): the new values equal the newest terms row.
  - `care_plans_status_match` (BEFORE UPDATE OF status): the new status equals the newest status-log row.

  Leave `time_logs.locked_at`, `care_plans.auto_issue` and `last_billed_period` unused, and say so in schema comments. `pnpm db:generate` leaves no diff, and the migration guard passes.

**2. Core, pure.** Coverage ≥ 90 %. Add `care.ts` and `time.ts` to `MONEY_FILES`. New subpaths `./care`, `./time`, `./dashboard`, `./stats`.
- **`packages/core/src/care.ts`:**
  - **Periods:**
    - `periodOf(date, billingDay)`: from the latest date ≤ the given date whose day is the billing day, up to the day before the next one.
    - `planPeriodOf(date, {billingDay, startDate})`: clamps the first start to the start date; `null` before it.
    - `previousPeriod`, `nextPeriodStart(today, billingDay)`, and `lastPeriods(today, plan, n ≤ 12)`.
    - `periodStartSql(dateExpr, dayExpr)`: the same rule as SQL (`CASE WHEN CAST(strftime('%d', d) AS INTEGER) >= b THEN date(d,'start of month','+'||(b-1)||' days') ELSE date(d,'start of month','-1 month','+'||(b-1)||' days') END`), the TypeScript twin of `periodOf`, with a test.
  - **History lookups:** `termsOn(terms, date)` and `statusOn(log, date)` return the newest row ≤ the date (ties broken by `createdAt`, then `id`). `hasAllowance(P) = statusOn(P.start) === "active"` (Q5).
  - **`carePeriodUsage(input)`** returns `{ period, included, rolloverIn, available, used, nonBillable, remaining, overageMinutes, overageMinor | null, rateMissing, burnBp | null, flag: "none" | "near" | "reached" }`:
    - `included` = `hasAllowance(P) ? termsOn(P.start).includedMinutes : 0`
    - `rolloverIn` = `hasAllowance(P−1) && termsOn(P−1.start).rollover === "one_month" && P−1 is a plan period ? max(0, included(P−1) − used(P−1)) : 0` (never compounds; Q3)
    - `used` = billable minutes only; `nonBillable` is separate (Q2)
    - `overageMinutes` = `max(0, used − included − rolloverIn)`
    - `overageMinor` = `divRoundHalfUp(BigInt(overageMinutes) × BigInt(rate), 60n)`; when there is no rate, `null` plus `rateMissing`
    - the flag is set only when `available > 0`: `used × 10000 ≥ 8000 × available` → `near`, `≥ 10000 × available` → `reached`; `burnBp` by bigint floor division
  - **For M5.4:** `overageQuantityMilli(minutes)` = `minutes × 1000 / 60`, and it throws unless `minutes % 15 === 0`. With 15-minute steps, the tax engine's half-up quantity × rate gives exactly this amount.
  - **Rules:**
    - `CARE_TRANSITIONS`: active → paused | cancelled; paused → active | cancelled; cancelled is terminal.
    - `termsEffectiveFrom(today, plan)`: the start date if the plan hasn't started yet, else `nextPeriodStart` (Q1).
    - `statusEffectiveOn(today, plan)` = `max(today, startDate)`.
    - Constants `CARE_NEAR_BP = 8000` and `CARE_REACHED_BP = 10000`.
- **`packages/core/src/time.ts`:**

  - `authorLocked(createdAt, now)` = `now ≥ createdAt + 7 × DAY_MS`.
  - `weekOf(date)`: Monday to Sunday, IST.

### Tests (failure paths first)
**Time**
- **Day cap:**
  - 1440 already logged plus 15 → 409 `day_cap`.
  - Raw INSERT and UPDATE past 1440 → abort.
  - 10 parallel 180-minute creates → exactly 8 succeed.
- **Target:** neither or both targets → 400, and the raw statements abort.
- **Plan status on the work date:**
  - On or after the pause → 409 `plan_not_active`; the day before → 201.
  - Before the start, or a cancelled plan → 409.
  - Moving an entry into a paused date → 409.
  - Pause and resume on the same day → that day is active.
  - A pause before the start takes effect on the start date.
- **Projects:** a cancelled project → 409 `project_closed`; a completed project is accepted.
- **Lock:** the author at `created + 7 d − 1 ms` can edit; at `+ 7 d` → 403 `time_locked`. The owner after the lock → 200, with `lockOverride`.
- **Other people's entries:** staff or Sales on another person's entry → 404; the accountant writing → 403.
- **Dates:**
  - `today − 8` without `writeAny` → 403 `owner_only_date`; `today − 7` → 201.
  - Tomorrow (IST) → 400 `future_date`.
  - The IST midnight edge: 2026-11-30 18:29 UTC vs 18:30 UTC.
- **Logging for others:** staff with `userId ≠ self` → 403; the owner for an inactive member → 400.
- **Minutes:** 0, 10, 1445, 1455 and non-integers → 400; 15 and 1440 → 201.
- **Versions:** a stale version → 409 on PATCH and DELETE.
- **Scoping:**
  - Staff `?userId=other` → 403.
  - A deep scan finds no one else's entry in any staff or Sales response.
  - The accountant reads all entries.
  - Week totals equal the sum of the entries (a fixture plus fast-check).

**Care plans**
- **RBAC:**
  - Staff POST /terms → 403; staff cancel → 403; staff pause and resume work.
  - Sales and the accountant writing → 403; signed out → 401.
  - An RBAC loop over every new route for all 4 roles.
- **Transitions:** invalid ones → 409; cancelled is terminal.
- **Raw SQL:**
  - Updating the price without a terms row → abort; updating the status without a log row → abort.
  - UPDATE or DELETE on a history table → abort.
  - Changing billing day, client, currency or start date → abort.
- **Inputs:**
  - `includedMinutes % 15 ≠ 0` → 400, and the CHECK refuses it too.
  - An anonymised individual client → 409 `client_anonymised`.
  - The currency always equals the client's.
