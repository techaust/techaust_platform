- B: the refund first, then the credit note is drafted for you. Until you issue it, the invoice would show money owed again, so it would also need a "refund waiting for its credit note" state that stops reminders and the Pay button. More moving parts.

**Q2. The back-up way to make receipt PDFs** (on 2026-10-25 you moved "the pdf-lib receipt fallback" to M6). - **A (Recommended):** drop the back-up; receipts queue like every other PDF and are made as soon as the browser service is free.

**A refund, step by step:**
1. **Read, then `planRefund`.**
   - From a document: the amount must not exceed this payment's net allocation to the document (409 `exceeds_holding`), and the excess (paid + credited + TDS − total) must cover it. Otherwise 409 `credit_note_needed` with `excessMinor` and core `creditNoteDeadline` for the dialog's "draft a credit note" step (Q1 A).
   - An export invoice: 409 `export_refund_unconfirmed` until `confirmExport: true` (the FEMA warning, M).
2. **Batch 1** (≈ 7 statements):
   - main: the refund INSERT (gateway `requested`, manual `succeeded`); the WHERE holds the Owner session with step-up, a live client, the confirmed source, the refundable in SQL (the same two cases as `payment_refunds_bounds`: from credit, amount ≤ unallocated; from a document, amount ≤ min(excess, holding)), and no open refund;
   - audit;
   - side, in this order (review fix 1): the release (`allocationsInsertStatement`), then a guarded `UPDATE payment_refunds SET release_allocation_id = <release id> WHERE id = ?refund AND release_allocation_id IS NULL` (set once in `payment_refunds_fixed`; the refund row is inserted with it NULL, so the foreign key is never checked against a row not yet written), the recompute, and a resolve of the review item when the refund came from one; re-count the statements (≈ 7);
   - last: `ledger_result` (unguarded).
3. **Gateway only:** `gatewayCallAllowed` is checked in the route **before batch 1** (live with the flag false → 503 `live_not_allowed`, zero fetches and **nothing written**, review fix 3); after batch 1, call the provider's `refund` with `AbortSignal.timeout(8000)` and the refund id as the idempotency key.
   - **Accepted:** batch 2 (2 statements: status `processing` or `succeeded`, `provider_refund_id`; an audit row with actor `system`).
   - **4xx refusal:** batch 2 → `failed` with `failure_code`. The released money **stays as credit**, never back on the invoice. Answer 502 `gateway_refused` {code}.
   - **Network error or 5xx:** the row stays `requested`. Answer 202 `{status: "requested"}`. `refund.sweep` settles it.
4. **Partial failures, each pinned by a test:**
   - D1 fails before the call: no refund is sent.
   - The gateway succeeded but batch 2 failed: the webhook or the sweep finds the refund by our id (`receipt`, metadata or request id) and moves the row.
   - The gateway answer was lost: the retry reuses the same idempotency key (Stripe, PayPal); for Razorpay, a lookup by `receipt` first, then adopt.
   - `cancel` is allowed only after the provider shows no refund for our id.
5. **No reject or withdraw of a gateway payment.** Money to return from a pending gateway payment is first confirmed to credit (M6.2's verify path, no allocation), then refunded from credit (L6).

**`GatewayEvents.processEvent`**, refund branches (generic dispatch on `webhook_events.provider`):
- **A refund event for one of our refunds:** one batch (≤ 4: refund move, event processed, audit `system`, an owners' bell on `failed`).
- **Unknown refund** (made in the gateway's dashboard), **dispute or reversal:** a review item (`refunded_outside`, `dispute_opened`, `dispute_closed`, `reversed_after_confirm`) and a bell, **no ledger move**. The Owner records it through the refund route with `outside`, which then holds every ledger rule (L7).
- **Not ours** (Stripe shared account, M6.3 L5): 200, no D1.

**`BillingJobs` (finance.ts), new methods:**
- **`issueReceipt({paymentId})`** → `issued | already_issued | not_eligible`:
  - **read first:** an existing `rct_` row → `already_issued`;
  - **one batch** (≈ 7 statements, the M5.1 issue shape with every guard in the main statement): counter row, counter bump, INSERT the frozen receipt with the number from `doc_counters`, link the payment, audit `receipt.issue` (actor `system`), `issue_result` unguarded;

### N. Lead decisions (for 13; accepted by the lead 2026-11-01, with review round 1's fixes)
- **L1:** a refund draws on a payment's **unallocated** money. A refund from an invoice writes the refund row (guarded main statement), then the `release`, then links the two, in one batch, so the M6.1 recompute and `documents` stay unchanged; refunds are subtracted wherever credit or "collected" is read (A3).
- **L2:** refund ≤ refundable is held in four places: core `planRefund`, the insert's WHERE, `payment_refunds_bounds` (from credit: amount ≤ unallocated; from a document: amount ≤ min(excess, holding)), and M6.1's release clause (release = the refund amount, ≤ excess and ≤ holding), with `ledger_result` (net + refunds ≤ amount) at the end of the batch.
- **L3:** receipts are issued in their own batch, through `receipt.issue` on `PDF_QUEUE` → `BillingJobs.issueReceipt`, never inside a confirm batch (the advance batch is ≈ 37 statements before T11). An hourly sweep catches misses.
- **L4:** a receipt is a `documents` row of type `receipt` with `id = 'rct_' + payment id`, series `receipt`, numbered at issue (receipt date = the issue day; "Received on" = `received_on`); `header_extras.receiptOf` sealed; no signature block.
- **L5:** receipts for every confirmed `payment` row (never `tds`), back-catalogue included; email only within 3 days of confirmation.
- **L6:** no reject or withdraw of gateway payments; a refund always comes from confirmed money.
- **L7:** outside refunds, disputes and reversals become review items only; the Owner records the ledger move.
- **L8:** one open refund per payment; a failed refund leaves the money as credit.
- **L9:** "Collected" = confirmed payments − succeeded refunds by `settled_on`; the payments register gains refund rows (a new layout version if the CSV has one).
- **L10:** a withdrawn payment's receipt is voided in the withdraw batch, with no client email; a payment with a refund not `failed` can't be withdrawn (409 `refunds_exist`).
- **L11:** reconciliation is Razorpay's settlement API plus an Owner "seen in bank statement" tick (`payments.reconcile`, Owner only); bank CSV import is a follow-up.
- **L12:** the ₹25 lakh check is a warning (PRD), using the newest Owner-typed USD rate (`fx_rate_micros` and its date); "rate unknown" past 30 days; M6.3's hard cap stays.
- **L13:** EDF "Amount realised" = the export invoice's `paid_minor`, through `edf-v2`.
- **L14:** TDS after a full credit note: the TDS part stays "refund due" until the Owner records the client's word:
  - "client revised its TDS return" → withdraw the TDS entry, reason `tds_return_revised` (check that M6.1's withdraw takes `tds` rows);
  - "paid back" → a `tds_payback` refund through the narrow trigger exception in A.

  **Build choice (lead, review fix 7):** the "client revised its TDS return" record is built in M6.5 (it records a fact and decides no law). The `tds_payback` path is built only if RA-30's OPEN point ("decide with M6.5", 08-C) is settled on the safest reading before B1 so that the TDS part is owed back; otherwise it stays a follow-up and the TDS part shows "refund due" until the Owner records the client's revised return.
- **L15:** an anonymised client stays locked: no refund (409 `client_gone`), and anonymising is refused while a refund is open.
