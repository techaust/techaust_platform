4. **Bindings and config.** Which bindings move (D1, R2 `FILES`/`DOCS`, `EMAIL_QUEUE`, `PDF_QUEUE`, secrets) per environment (local, staging, production with none until Phase 7); `wrangler types` for both; the Vite plugin with an auxiliary Worker; the CI guards that must cover the new Worker (`check-worker-config.mjs`, `worker-budget.mjs`).

## Analyst draft (Opus 5.5 high, 2026-10-27): summary
The full draft is in the lead's conversation. Measured with an esbuild 0.28.2 metafile (+0.6 % against the real rolldown bundle).
- Today: 417,930 bytes by esbuild (real 415,296), startup proxy 37.5–39.0 ms.
- **Front** (SPA assets, `/v1/health`, `/v1/auth/*` from `auth.ts` and `account.ts`, `/v1/users/*`, and a forwarder): 97,226 bytes, startup 8.7–9.2 ms.
- **API** (every other route): 383,733 bytes, startup 41.5–41.7 ms. It holds no sign-in code and no secrets (the five secrets are read only in `auth.ts` and `account.ts`; the lead checked by grep).
- `users` stays in the front: `users.ts:12` imports `json` from `auth.ts`, which would pull the whole auth router into the API (+30 KB).
- Peeling off one route group at a time saves almost nothing (`document-warm.ts`, `leads.ts` and `client-tabs.ts` cross-import the documents code), so a three-Worker split would duplicate about 200 KB today. Two Workers now.
- Forwarding by plain `fetch` over the binding (`env.ADMIN_API.fetch(c.req.raw)`), registered before any front middleware. The API Worker runs today's middleware chain and guard and re-authenticates from the cookie. No trusted context crosses the binding, so there is no fake-actor door.

## Lead's check of the draft (2026-10-27)
Checked against the Cloudflare docs (docs MCP, read-only):
- **Requests:** a call through a service binding is billed as part of the first request, not as a second one (developers.cloudflare.com/workers/platform/pricing/#service-bindings, "only on Workers Standard pricing"). Staff traffic is far below the Free plan's 100,000 a day either way.
- **Limits:** each binding call counts toward the caller's subrequests, and one request may chain at most 32 Worker invocations (/workers/runtime-apis/bindings/service-bindings/#limits). One forward per request is fine.
- **CPU:** pricing bills "the total amount of CPU time used across both" Workers; the limits page says 10 ms "per HTTP request" without saying whether a bound Worker gets its own 10 ms. **Lead decision:** plan for the safe reading, the sum (LD7). The front's forward costs well under 1 ms, so today's work fits as before; the split buys bytes and startup room, not CPU.
- Still unverified until the builder's dry runs and the first staging deploy: the Vite auxiliary-Worker output path and deploy, the vitest pool with the binding, header and body fidelity (`CF-Connecting-IP`, `Content-Length` for uploads), per-Worker invocation logs, the `wrangler rollback` flags.

## Lead decisions (docs/13, 2026-10-27)
- **LD1** Two Workers: front `techaust-platform-admin` and API `techaust-platform-admin-api` (`-staging`). Forwarding by `fetch` over the `ADMIN_API` binding; the API Worker re-authenticates from the cookie, holds no secrets and has no public URL at any level.
- **LD2** `ROUTES` stays the one source; `RouteDef.on?: "front"` marks health, `/auth/*` and `/users/*`.
- **LD3** Ceilings in `scripts/worker-budget.mjs`: front 150,000 bytes, API 800,000 bytes, startup ≤ 200 ms each; forbidden markers in the API bundle: `auth_attempts`, `totp_secret_enc`, `pw_hmac`. A third Worker is planned when the API passes 650,000 bytes or its cold reading passes 7 ms.
- **LD4** The front keeps declaring `FILES`, `DOCS` and `PDF_QUEUE` for now, so one generated `Env` stays complete (follow-up: drop them from the front once the shared modules are typed per Worker).
- **LD5** A binding failure answers 502 with the standard error body and one error log line (the route pattern, not the path); no access row.
- **LD6** One `{ev:"fwd", r, s, rid, iso, n}` log line per forward, with the same keys as `ev:"req"`.
- **LD7** CPU gate for a forwarded request: front + API ≤ 7 ms p99, none over 10 combined.

## Builder brief (lead, 2026-10-27)
**Model:** Sonnet 5.5, medium (Tier B). **Branch:** `feat/m5.0-builder` from `origin/feat/m5.0-admin-split`, in its own worktree; push only that branch. **Skills:** `cloudflare:workers-best-practices`, `cloudflare:wrangler`, `cloudflare:workers-profiling`; list them in the report.

**Rules:**
- no change to behaviour, copy or screens;
- no hosted changes: no deploy, no `wrangler login`, no resource creation (`--dry-run` only);
- heavy commands go through `bash tools/heavy.sh --log <name> <command>`, one at a time; never read whole logs;
- commit at least every 20 minutes and at each layer;
- stop every dev server before reporting; stop and report when blocked;
- check current docs (context7, or the installed schema and types) for `auxiliaryWorkers`, `services` and the vitest plugin rather than guessing.

**Contract:**
- The front Worker serves the SPA plus the rows marked `on: "front"`.
- For every other `ROUTES` row it returns `c.env.ADMIN_API.fetch(c.req.raw)` untouched (no header or body changes, the Response not wrapped), registered before any middleware.
- An undeclared path gets a 404 from the front and is never forwarded.
- The API Worker runs the existing middleware chain (logging, CSRF, body limits, guard) with only the API rows, and answers 404 for front rows and undeclared paths.

**Layer 1: factory and route ownership** (still one Worker; bundle within ±1 KB)
- `worker/context.ts`: `RouteDef.on?: "front"`.
- `worker/guard.ts`: mark the front rows (health, `/auth/*`, `/users/*`).
- New `worker/app.ts`: today's middleware chain from `worker/index.ts`, as `createApp(mounts, opts)`. Static imports only, no `import()` (docs/13 2026-10-25).
- New `worker/routes-front.ts` and `worker/routes-api.ts`, in today's mount order.
- Split `worker/warm.ts` into `warm-front.ts` (`warmStepUp`) and `warm-api.ts` (the rest).
- New test-only `worker/test-app.ts` mounting both; point `test-helpers.ts`, `rbac.test.ts` and `route-lookup.test.ts` at it.

**Layer 2: entries, forwarding and config**
- `worker/index.ts` becomes the front entry: front routes plus forwarders, LD5's 502 and LD6's log line.
- New `worker/api.ts` entry: `createApp(api) satisfies ExportedHandler<Env>`.
- New `apps/admin/wrangler.api.jsonc`:
  - the same compatibility date and flags as the front;
  - `workers_dev: false` and `preview_urls: false` in every scope;
  - no `routes`, `route`, `assets`, `previews` or `secrets`;

  - production has vars only (no D1, R2 or queues until Phase 7);

- `wrangler.jsonc`: `services: [{ binding: "ADMIN_API", service: … }]` in every scope, because it isn't inherited. Top level and production point at `techaust-platform-admin-api`, staging at `techaust-platform-admin-api-staging`.

**Layer 3: guards**
- `scripts/check-worker-config.mjs`: check a list of config paths.
  - The API config follows LD1's rules in all three scopes, and its D1, R2 and queue names match the front's in each scope.
  - The front has `ADMIN_API` in all three scopes, pointing at the API config's name for that scope.
- `scripts/worker-budget.mjs`: LD3 (front 150,000; `adminApi` 800,000; the forbidden markers).
- Update `packages/core/test/worker-budget.test.ts` and `apps/web/test/worker-config.test.ts`. The new config passes; each of these fails: `workers_dev: true`, a `routes` entry, `secrets`, `previews`, a missing staging `services`.

**Layer 4: `worker/split.test.ts`**
- **Ownership:**
  - every `ROUTES` row has one owner;
  - the front app's routes equal the front rows, and the API app's equal the API rows;
  - every API row is non-public.
- **Forwarding fidelity:** for every API row (`sampleRequest`), the front with a recording stub:
  - forwards exactly once, with the same method, URL, headers (`Cookie`, `Origin`, `Sec-Fetch-Site`, `Content-Type`, `Content-Length`, `User-Agent`, `CF-Connecting-IP`) and body bytes;
  - makes zero D1 calls and writes no access row.

  Front rows never call the stub; an undeclared path is a 404 and is never forwarded.
- **Parity:** with the stub set to the API app over only the API Worker's bindings (no secrets, no `ASSETS`), every row gives the same status and error code through the front as through the combined app:
  - no cookie (401);
  - a role `decide()` denies (403);
  - step-up missing (403 `step_up_required`);
  - a cross-site POST (403);
  - a body over the limit (413);
  - an allowed request.
- **The API app called directly:** 401 on every row without a valid session; 404 on front rows and undeclared paths; 403 on a cross-site Origin.
- **Binding failure:** a throwing stub gives 502 with the standard body and one error log line with the pattern; a stub returning 500 passes through unchanged.
- **Upload:** a 1 MB raw-body upload, front → API, stores an object of the declared length, and the download streams it back.
- **Static check:** no `worker/*.ts` other than `auth.ts`, `account.ts`, `users.ts` and the test helpers names any of the five secrets.

**Layer 5: verification** (through `tools/heavy.sh`, one at a time)

- `pnpm --filter @techaust/admin dev` with both Workers: sign in, open Leads, a client, a document and its PDF, upload and download a file, save a setting. Then stop the server.
