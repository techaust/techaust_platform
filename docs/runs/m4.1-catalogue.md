### Tests
- **RBAC:** every write and publish route answers 403 for staff, sales and accountant; reads are allowed for all four; signed-out answers 401.
- **Validation:** a SAC that isn't six digits, a negative price, a schedule that doesn't sum to 10,000 bp, and a bad slug are all refused; a duplicate slug answers 409.
- **Price history:**
  - One row per changed price, with the old and new values and the actor.
  - No row when nothing changed.
  - History and update in one batch: a failing update writes no history.
- **Append-only:** UPDATE and DELETE on `templates`, `site_snapshots` and `catalogue_price_history` abort; DELETE on `catalogue_items` aborts.
- **Snapshot:**
  - It never holds an internal field: SAC, GST rate, deliverables, assumptions, exclusions, ids, timestamps.
  - Inactive and off-site items are absent.
  - The same data twice gives the same SHA (canonical JSON) and `unchanged: true`.
  - The mini/classic parity.
  - A web build with a published snapshot shows the new price (the `apps/web` loader test with a fixture file).
- **Templates:** a new version keeps the old one; rendering leaves no unresolved placeholder.
- **Leads:** service names come from D1, and the bundle line shows the seed gone.
- **Workflow:** the fetch script parses the wrangler JSON, writes nothing when there's no row, and fails on an error. Review the workflow files by reading them (no runner).

### Design notes and decisions I took
- Column names: the schema's `published_at` and `changed_at` are really `created_at` in D1 (`createdAt()`). The brief's SQL for the fetch said `ORDER BY published_at`; the script uses `created_at, id`.
- Body limit: the admin has a 16 KB request cap, so catalogue markdown fields are ≤ 2,500 characters each and a template body is ≤ 14 sections, ≤ 2,000 characters a section and ≤ 12,000 in total. M4.3's proposal wording may need more: a route-specific limit is then a lead decision.
- Entry codes must match `S` + 1 to 4 digits (the snapshot requires `^S\d+$`). Default-line descriptions are unique within an item (price history names a line by its description).
- Price history field names: `price_inr_minor`, `price_usd_minor`, `line:<description>:rate_inr_minor` / `rate_usd_minor`. Audit rows hold ids, `itemCode` (not `code`, which a test treats as a credential word), field names and counts only.
- Seeded templates: proposal and estimate for each of the five categories, plus one care-plan block and one terms block (no category): 12 rows, version 1, ADM-PROP-02 headings and placeholders only (placeholder list: `client.name`, `client.contact`, `company.name`, `proposal.validity_days`, `service.code|name|short|deliverables|assumptions|exclusions|schedule`). A new version with an unknown placeholder is refused (`unknown_placeholder`).
- Publish returns 201 `{sha256, unchanged:false, id, items}` when stored; 200 `{sha256, unchanged:true}` when that SHA is the newest; 422 `snapshot_invalid` with the failing paths (never values) when the catalogue cannot be published (for example an on-site item with unit `hour`, or no on-site item); a missing payment-terms setting also gives 422.

### Workflow notes
- `deploy-staging.yml`: new step "Fetch the published catalogue snapshot" after migrate and seed, before the Workers deploy; creds on that step only; a failed fetch fails the job; no row means no file.
- `publish-catalogue.yml` (new): `*/30 * * * *` and `workflow_dispatch`; runs only when `github.repository == 'techaust/techaust_platform'` on `refs/heads/main`; `permissions: contents: read`; existing secrets only (`CF_API_TOKEN_STAGING`, `CLOUDFLARE_ACCOUNT_ID`); `concurrency: deploy-staging`; fetch, then an exact-key `actions/cache` lookup `catalogue-<sha>`; on a miss it deploys **web only** (`pnpm --filter @techaust/web run deploy:staging`) and writes the marker file the cache saves when the job ends successfully; the production comment is included. The fetch script verifies the row's SHA-256 against its text and fails on any error.
- **Needs the lead: `actions/cache` is not pinned.** No pin for it exists in the repository, and I will not guess a commit SHA or call GitHub. The line is `uses: actions/cache@PIN_THE_FULL_COMMIT_SHA # v4`. Replace it with the full SHA of a reviewed release. Until then the scheduled run would fail at that step, so do not merge before pinning.
