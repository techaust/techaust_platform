### What to build (data, logic, API, workflow; no screens)
1. **Schema** (0026 generated, 0027 custom `catalogue_triggers`; ADD COLUMN, index and trigger only):
   - `UNIQUE site_snapshots_sha256(sha256)`.
   - Append-only triggers on `templates` (no UPDATE or DELETE; a new version per edit), `site_snapshots`, and `catalogue_price_history` (if it isn't already).
   - `catalogue_items_no_delete`.
2. **Core** (pure):
   - **`packages/core/src/catalogue.ts`:**
     - The entry schema for create and edit (`zod/mini`): every ADM-CAT-02 field; SAC of six digits; prices ≥ 0 or null; `gstRateBp` 0–10,000 or null; default lines; schedule steps summing to 10,000 bp; the slug pattern (uniqueness is left to the DB).
     - `priceChanges(old, next)`: the history rows for INR, USD and every default-line rate.
   - **`snapshotFromRows(rows, settings)`:** builds the public snapshot with only the fields `catalogue-snapshot.ts` allows, from items that are both `show_on_site` and `active`.
   - **A `zod/mini` twin of the snapshot schema**, with a parity test against the classic one covering the seed snapshot, the current fixtures and the internal-field rejections from `test/catalogue-snapshot.test.ts`.
   - **`renderTemplate(body, data)`:** returns `{ text, unresolved: string[] }` for `{{client.name}}`, `{{service.*}}` and the other ADM-CAT-03 placeholders. A test shows every seeded template renders with test data and leaves no unresolved placeholder.
3. **Routes** (each a `ROUTES` row):

   | Route | Action | Audit |
   |---|---|---|
   | GET /catalogue (keyset 25/50; category, active and on-site filters; `q` prefix on code or name) | `catalogue.read` | none |
   | GET /catalogue/:id (the item and its price history, ≤ 50 rows, keyset) | read | none |
   | POST /catalogue | `catalogue.write` | catalogue.create |
   | PATCH /catalogue/:id (`expectedUpdatedAt`, else 409; code immutable; price changes write `catalogue_price_history` rows in the same batch, with `changed_by`) | write | catalogue.update |
   | POST /catalogue/:id/active `{active}` | write | catalogue.activate / .deactivate |
   | GET /templates · GET /templates/:id · POST /templates (a new version of a kind and category) | read / write | template.version |
   | POST /catalogue/publish (build the snapshot from D1 plus the payment-terms settings, validate with the mini twin, take the SHA-256; insert it unless that SHA already exists, then answer 200 `{ sha256, unchanged: true }`) | `catalogue.publish` | catalogue.publish |
   | GET /catalogue/snapshots (the last 20: SHA, who, when) | read | none |
4. **Leads stop importing the seed:**
   - `apps/admin/worker/leads.ts` reads service codes and names from `catalogue_items` (D1) instead of `@techaust/db/catalogue`, saving about 6 KB.
   - Keep the "not-sure" code.
   - Test that a renamed item shows its new name.
5. **Seed:**
   - It stays insert-only, so admin edits survive every deploy. Test: re-running the seed SQL doesn't revert an edited item.
   - Seed one template per kind and category, made only of the ADM-PROP-02 section headings and placeholders.
6. **Website build reads the published snapshot:**
   - **`deploy-staging.yml`:** before building web, fetch the newest snapshot into `apps/web/catalogue-snapshot.json` with:
     `wrangler d1 execute DB --remote --env staging --json --command "SELECT json, sha256 FROM site_snapshots ORDER BY published_at DESC LIMIT 1"`
     No row means no file (the seed is used). A failed fetch fails the job: never fall back to the seed silently when a snapshot exists (the M2.2 follow-up).
   - **New `.github/workflows/publish-catalogue.yml`** (the owner's answer):
     - Triggers: `schedule: "*/30 * * * *"` and `workflow_dispatch`. It runs only on this repository's `main` (a `github.repository` check; schedules never run for forks).
     - It reads the newest SHA the same way. If `actions/cache` (SHA-pinned, like every action) has no entry `catalogue-<sha>`, it builds web with the snapshot, deploys **web only** with `--env staging`, then saves the cache entry. Otherwise it exits early.
     - Existing secrets only; `permissions: contents: read`; `concurrency` shared with `deploy-staging`.
     - A comment that production follows the normal approved deploy (ADM-CAT-05).
   - Both workflows share one script, `scripts/fetch-catalogue-snapshot.mjs`, tested with fake `wrangler` output.
7. **Search:** a catalogue group (code and name prefix) for `catalogue.read`.

### Rules
- CLAUDE.md conventions:
  - keyset ≤ 50 and an index on every filter;
  - `zod/mini` as a namespace in Worker code, and no classic zod in the admin Worker (the budget guard fails it);
  - no `import()`, and schemas at module top level (add samples to `warm.ts`);
  - prices only in minor units.
- Audit rows hold ids, codes and field names only.
- API errors are codes; the screens map them to copy, which the lead drafts.
- Existing tests change only on purpose; name each one.
- Heavy commands via `bash tools/heavy.sh --log <name> …`.
- Commit every 20 minutes and at each finished layer. Run the whole-repo lint once, at the end.

### Tests
- **RBAC:** every write and publish route answers 403 for staff, sales and accountant; reads are allowed for all four; signed-out answers 401.
- **Validation:** a SAC that isn't six digits, a negative price, a schedule that doesn't sum to 10,000 bp, and a bad slug are all refused; a duplicate slug answers 409.
- **Price history:**
  - One row per changed price, with the old and new values and the actor.
  - No row when nothing changed.
  - History and update in one batch: a failing update writes no history.
- **Append-only:** UPDATE and DELETE on `templates`, `site_snapshots` and `catalogue_price_history` abort; DELETE on `catalogue_items` aborts.
- **Snapshot:**
  - It never holds an internal field: SAC, GST rate, deliverables, assumptions, exclusions, ids, timestamps.
  - Inactive and off-site items are absent.
  - The same data twice gives the same SHA (canonical JSON) and `unchanged: true`.
  - The mini/classic parity.
  - A web build with a published snapshot shows the new price (the `apps/web` loader test with a fixture file).
- **Templates:** a new version keeps the old one; rendering leaves no unresolved placeholder.
- **Leads:** service names come from D1, and the bundle line shows the seed gone.
- **Workflow:** the fetch script parses the wrangler JSON, writes nothing when there's no row, and fails on an error. Review the workflow files by reading them (no runner).
