## Phase 2 build brief (analyst draft, Opus 5.5 high, 2026-10-26; accepted above)
### The five points that matter most
1. **M4.5 needs migrations. The batch plan says "M4.5 none", and that no longer holds.** Two things already in the database block the work:
   - `doc_access_tokens` has `CHECK(purpose in ('view_pay'))` (0000_init.sql:551) and no contact column. A proposal link bound to a contact would need a table rebuild.
   - `acceptances` is append-only (`triggers.ts:153`), so `certificate_r2_key` can never be filled in after the certificate renders.

   The plan below uses new tables, ADD COLUMN and new triggers only (0034/0035). It rebuilds nothing. Lead decision LD1.
2. **The portal Worker may not name a `staff_` table** (a source scan enforces it, `scope.ts`). So the bell rows and the TecHaust-side emails on accept and decline can't be written by the portal. They go through a jobs expansion message, the same way as `staff.alert`.
3. **Contact erase would break on foreign keys.**
   - `documents.decided_contact_id` points at contacts and is set-once, and erase DELETEs the contact row (`clients.ts:1264`).
   - `CONTACT_ON_ISSUED_DOCUMENT_SQL` must also block a contact who declined. It already covers acceptances.
   - The M3.3 erase/anonymise batch must clean up the new link and send tables. VERIFY WITH CA/LEGAL.
4. **The portal's HTML view should come from the same R2 envelope and the same `toPdfView()` that made the PDF.** That makes it match the PDF by construction, and it is cheap (the M4.4 proxy: parse 0.16 ms).
   - **But the envelope must never be streamed raw.** Its lines carry `catalogueRateMinor` and `catalogueItemId`, its sections carry `hidden`, and its issuer carries `sender.staffId` (`packages/pdf/src/types.ts:66-81, 39`). Only the projected `PdfView` goes to the client.
5. **The confirmation email goes after the certificate renders**, because the approved email links both the accepted PDF and the certificate. The accepted state shows at once in the portal and the bell fires at once. On a day the Browser Run quota runs out, the email waits until the next UTC day. Lead decision LD6.

### Lead decisions this brief rests on (record in docs/13 when accepted)
- **LD1. Migrations:** new tables, ADD COLUMN, CREATE INDEX and new triggers only; no rebuild and no `check()` on an existing table (above).
- **LD2. Offer links are their own table, `offer_links`, not `doc_access_tokens`.**
  - Each link is bound to one contact and grants its **version group** (one offer, every version), never other offers of the same client.
  - The owner approved accepting from the link (docs/13 row 212).
  - Allowed `purpose` values (`offer`, `confirmation`) are enforced by a **trigger, not a CHECK**, so a future purpose is a trigger swap, not a rebuild (the lesson of `doc_access_tokens`).
- **LD3. Link lifetime:**
  - an offer link lasts until the end of `valid_until` (IST) + 30 days;
  - a confirmation link lasts 90 days from the acceptance.
  - Both are revoked by a staff revoke, by portal access turned off, by an email change or by anonymisation. The read also joins the live contact, the same switch the session uses.
- **LD4. Emails go only after the PDF exists:**
  - the send batch writes `document_sends` rows marked "waiting";

### Races and idempotency (each one gets a test)
| Case | What decides it |
|---|---|
| Double accept (two tabs, two contacts) | The unique `acceptances_document` plus the group `NOT EXISTS` inside one batch. Exactly one acceptance, one audit row, one lead move, one certificate message. The same contact's repeat → 200 replay. |
| Accept vs sending v2 | Accept requires "no newer frozen version"; the v2 freeze requires "nothing accepted in the group" (M4.3). Either order: one wins, the other 409s (`superseded` / `already_accepted`). |
| Accept vs revise (draft only) | Allowed. Afterwards v2's send is refused (`already_accepted`). |
| Accept after expiry (job not yet run) | `valid_until >= todayIst` in the WHERE. Boundaries at 18:29:59.999 and 18:30:00 UTC. |
| Accept vs the expiry job | Both conditional on `status IN ('sent','viewed')`; the first to commit wins. |
| Accept vs decline (two contacts) | Both conditional on status; the second → 409 `already_decided`. |
| Accept vs link revoke, or vs portal access off | Live-link and live-contact `EXISTS` in the INSERT. |
| Start project double click | `projects_source_document` and `documents_source` (step 1); the second → 200 `created: false`; one project, one set of milestones, one draft. |
| Redelivered `offer.send` / `offer.accepted` | `email_log` id per (template, entity, address); extra links stay valid; no revoke on re-mint. |
| `onRendered` twice, or sweep plus `onRendered` | `offer.send` is idempotent; `queued_at = coalesce(…)`. |

### Tests (failure paths first)
- **Cross-tenant:** the `crossTenant` harness (`test-helpers`) on every new portal route: another client's id → 404 with the same body; a link of group A can't read group B of the same client; a SQL spy proves every portal statement binds `client_id = ?1` or goes through a scoped parent; a source scan proves no `staff_` table appears in portal SQL.
- **Token path:**

- **Accept refusals:** `pdf_sha256` NULL → 409 with nothing written; expired (including the IST boundaries); superseded; a newer frozen version while the old status is still `sent` (forced with SQL); already accepted; declined; `agree` false or missing; `typedName` empty, only spaces, control or bidi characters, > 120 characters; forbidden extra fields → 400; anonymised client; cross-site Origin → 403; not JSON → 415; > 16 KB → 413.
