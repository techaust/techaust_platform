**Choices for the analyst to look at:**
1. **`turnstile_required` counts nothing at all, the per-address `ip:` counter included**, as the brief says. Consequence: a script with no token can write one `access_log` row per request for any email that stands at 3 or more failures (an unknown email too, after 3 attempts). The `locked` path avoids this by counting a failure for the address. Suggest adding `ipFail` to that `logBatch` (it only hurts the sender). Not done, because the brief said "counts nothing". Decide.
2. **`queueSender(env)`, not `(env, executionCtx)`.** The route owns `c.executionCtx.waitUntil(...)` for any sender (the injected test sender too), so "the response never waits" holds for every sender. `Vars.sender` is now optional (absent in production). `MagicLink` gained `tokenHash` and `expiresAt`.
3. The 2FA alert `reset_by_owner` is about the member, but the device and place in its row are the owner's browser. The copy must not say "from your device".
4. Data fallbacks I had to pick: "Unknown location" and "Unknown browser" (the user-agent reader's own words). The lockout email data has no lock length (jobs has no dependency on `@techaust/auth`; adding one changes the lockfile).
5. Placeholder bodies are marked "PLACEHOLDER"; the owner lockout subject has no approved line (07-G pending) and reads `PLACEHOLDER (copy pending 07-G): ...`.
6. `RESERVE_GATED_SQL` also refuses when the lock has ended but 3 or more failures stand and the token is missing: `turnstile_required`, not a free attempt.
7. The check runs before the address-block read, so a blocked address that sends a token still costs one siteverify call (no write).
8. Admin `ipKey` now counts IPv6 by /64; an IPv4 key is unchanged.
