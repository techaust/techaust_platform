### Step 1: builder (Sonnet 5.5, high)
**First:** load `cloudflare:workers-best-practices`, `cloudflare:wrangler`, `cloudflare:cloudflare`, `cloudflare:turnstile-spin` (siteverify only; never run its wizard or scripts), `cloudflare:workers-profiling`, `aws-core:aws-messaging-and-streaming`; list them in the report. **Never touch hosted services:** no deploy, no `secret put`, no remote D1, no Turnstile or AWS API calls, no installs.

1. **Shared Turnstile helper** (`packages/auth/src/turnstile.ts`, exported from `index.ts`): move `turnstileOk` out of `apps/web/src/forms.ts` as `verifyTurnstile({ secret, token, remoteip, action, hostnames, local })` → `boolean`. Empty or > 2,048-character token refused without a fetch; POST form-encoded with `AbortSignal.timeout(5000)` inside the request only; require `success === true`; outside `local` require the exact `action` and a listed hostname; fail closed on network error, non-2xx or non-JSON. Web forms use it with behaviour unchanged (existing web tests pass unchanged).
2. **Schemas** (`packages/auth/src/schemas.ts`, `zod/mini`): `magicRequest` gains a required `turnstile` (1–2,048); `loginRequest` an optional one.
3. **Gated reservation** (`packages/auth/src/attempts-sql.ts`, `lockout.ts`): `RESERVE_GATED_SQL` = `RESERVE_SQL` + binds `?7` (Turnstile verified 0/1) and `?8` (`TURNSTILE_AFTER` = 3). The DO UPDATE branch counts only when the lock is over and `?7 = 1`, or the window has expired, or `failures < ?8`; the INSERT always counts. A pure twin `reserveAttemptGated` and an agreement test, as for `RESERVE_SQL` / `reserveAttempt`. `RESERVE_SQL` stays byte-for-byte unchanged.
4. **Admin `/login`** (`apps/admin/worker/auth.ts`): validate JSON → if a token is present, `verifyTurnstile` (action `admin_login`, `remoteip` = `CF-Connecting-IP`) → `tv` → ONE batch `[IP_READ, acct pre-read (window_start, failures, locked_until), RESERVE_GATED_SQL(acct:, …, tv), LOGIN_READ]` → address blocked: the existing 429 → nothing reserved: pre-read locked → the existing 429 `locked`, else **401 `{code:"turnstile_required"}`** (writes the access row like every admin refusal; counts nothing) → otherwise as today. Unknown emails are counted the same. A normal sign-in (< 3 failures) makes no siteverify call. No Turnstile on `/salt`, `/totp`, `/recovery`, `/step-up`. Fold in: `ipKey` counts IPv6 by /64 with `addressOf`, with a test.
5. **Staff alerts → emails** (`apps/admin/worker/{alerts,auth,account,users}.ts`): `alertStmt` takes a pre-made `uuidv7()` and returns `{ stmt, id }`. The 2FA summary gains `change`: `recovery_code_used` | `recovery_codes_regenerated` | `reset_by_owner`; otherwise exactly `{ua, country, city}`, no IP. After the batch, for each alert whose statement changed one row, `c.executionCtx.waitUntil(c.env.EMAIL_QUEUE.send({ kind: "staff.alert", auditId }))` (never destructure `ctx`); a failed send logs a code-only line and the response is unaffected. `new_device` only when its guarded insert ran (a new browser, not enrolment).
6. **Portal `/magic`** (`apps/portal/worker/{auth,sender,index}.ts`): validate JSON → `verifyTurnstile` (action `portal_link`, `remoteip` = the raw `CF-Connecting-IP`, never the /64); on failure **400 `turnstile_failed`**, nothing written, no access row, one code-only log line → the existing batch and quotas, unchanged. Replace `noSender` with `queueSender(env, executionCtx)`: one `EmailMessage` per link (`template: "portal.magic_link"`, `to`, `data: { url, org_name, expires_at }`, `entity: { type: "magic_link", id: tokenHash }`) sent with `ctx.waitUntil(EMAIL_QUEUE.sendBatch(...))`, so a known email never answers later than an unknown one. The `sender` injection in `createApp` stays for tests.
7. **Messages** (`packages/core/src/schemas/messages.ts`): `EMAIL_TEMPLATES` gains `portal.magic_link`, `staff.new_device`, `staff.2fa_change`, `staff.lockout`, `staff.lockout_owner`; new `staffAlertMessage` = `{ kind: "staff.alert", auditId: uuid }`; the email queue carries `emailMessage | staffAlertMessage`. Producers import types only, never the zod schema.
8. **Jobs** (`apps/jobs/src/{email,queue}.ts`, new `staff-alerts.ts`):
   - `staff.alert`: ONE D1 batch reads the audit row (action, entity_id, time, summary), the member (email, name, role, status) and, for a lockout, every active `owner`. Missing row → ack and log. Recipients: new device and 2FA change → the member if `active` or `invited`; lockout → the member (active or invited) plus each active owner, deduplicated. Then `EMAIL_QUEUE.sendBatch` of ordinary `EmailMessage`s, and ack. Data: time as "23 Oct 2026, 14:05 IST" from the `core` date helpers (no `Intl`); device from the user-agent reader, moved from `apps/admin/src/lib/user-agent.ts` to `packages/core/src/user-agent.ts` (the SPA imports it); location as city and `countryName`. Entity `{ type: "audit_log", id: auditId }`; lockout `{ type: "staff_lockout", id: "<userId>:<hour bucket>" }` (one an hour per person).
   - `portal.magic_link`: `now > expires_at` → `email_log` `skipped` / `expired`, ack.
   - DLQ: `processDeadLetter` handles both shapes, naming only the template or "staff alert", never the URL, token, address or summary; a dead-lettered magic link marks its `email_log` row `failed`.
   - No `data` value in any log line (test).
9. **`packages/email`:** `SENDERS.noReply` = `{ name: "TecHaust Technologies", address: "no-reply@techaust.com" }`, Reply-To per Q2. `renderEmail` cases for the five templates as plain placeholder HTML; subjects from 07 §8 / 07-G; bodies marked for the designer.
10. **Warm-ups:** a parse of a `portal.magic_link` email and a `staff.alert` message in `warmConsumerMessages`; each new template rendered once in `apps/jobs/src/warm.ts`; warm the user-agent reader; update the count tests. Synchronous or Web Crypto only; extend the start-up-rules test (`Request`, `Response`, `fetch`, `setTimeout`, `AbortSignal.timeout`, `getRandomValues` throw) to the new code.
11. **Config:** `apps/admin/wrangler.jsonc` and `apps/portal/wrangler.jsonc`, top level and `env.staging` (bindings are not inherited): `EMAIL_QUEUE` producer (`techaust-local-email` / `techaust-staging-email`); vars `TURNSTILE_SITE_KEY` and `TURNSTILE_HOSTNAMES` (the staging admin or portal host only); `TURNSTILE_SECRET` in `secrets.required` in every env, production included. Production gets no queue until Phase 7 (comment). The SPA reads the site key at build time from `wrangler.jsonc` for `CLOUDFLARE_ENV`, as web's `src/lib/turnstile.ts`; a staging build with an empty key fails. `pnpm dev:secrets` writes Cloudflare's always-pass test secret and site key for admin and portal; `.dev.vars.example` names only; `vitest.config.ts` injects test values; run `wrangler types`.
12. **CLI:** `pnpm portal:sample` gains `--email <address>` (one sample contact on a verified inbox for staging; the lead runs it with the owner's yes).

**No migration expected** (templates have no CHECK, `summary` is JSON, `auth_attempts` and `email_log` fit). If one becomes necessary: a new table, `ALTER TABLE … ADD COLUMN` or `CREATE INDEX` only; never rebuild `staff_users`, `contacts`, `audit_log`, `email_log` or `magic_link_tokens`. **Tests** (Vitest; workerd for the Workers; failure paths included):
- **Turnstile:** missing, empty or over-long token (no fetch for over-long); `success:false`; duplicate token (`timeout-or-duplicate`); wrong action (a web `contact` token at admin or portal); wrong hostname; siteverify network error, 5xx, non-JSON fail closed; local mode skips only action and hostname.
- **L8b:** 100 token-less `/magic` requests for one email leave `p:mail:` and `p:req:` untouched and a real request then succeeds; token-less `/login` never moves `acct:`.
- **Admin gating:** attempts 1–3 need no token; the 4th without a valid token → 401 `turnstile_required`, nothing counted; with a valid token it counts and checks as before; a lock still answers 429; a successful sign-in clears the counter; SQL and twin agree (property test); a normal sign-in makes no siteverify call (counted).
- **Enumeration:** `/magic` for unknown, known, no-access, anonymised and two-organisation emails: identical status, body (ignoring `request_id`), headers and D1 call count; a sender whose `send` never resolves still gets the response; the queue only through `waitUntil`; `/login` `turnstile_required` identical for unknown and known; lockout alerts only for real accounts.
- **Replay and single use:** existing link and token tests green; a magic-link message delivered twice sends once.
- **Queue and idempotency:** two organisations → two emails; two real requests within 15 minutes → two emails; expired → `skipped`; suppressed or not allow-listed on staging → `skipped`; a redelivered `staff.alert` → each email once; missing audit row → acked; lockout → member plus owners deduplicated, a second lock in the same hour sends no email but keeps its audit row; deactivated member → owner copy only; three 2FA variants carry the right `change`; new device only for a new browser; an invalid message acked and logged; DLQ text has no `#t=`, URL, address or summary.
- **Privacy:** no log line contains an email address, IP, token or URL; the admin queue message holds the audit ID only.
- **CPU:** warm-up count and start-up-rules tests; `scripts/check-admin-bundle.mjs` and `check-portal-bundle.mjs` pass; no `@techaust/email` and no full-zod import in admin or portal.
- **Config:** the web binding guard and the Worker-config guard pass.
