### B. Core (B1; pure; ≥ 90 % coverage; `stripe.ts` and the changed `online-pay.ts` stay in `no-floats.test.ts`)

**`packages/core/src/stripe.ts`** (subpath `@techaust/core/stripe`; no `fetch`, no zod; small, because jobs imports the verifier):

1. **`verifyStripeSignature(rawBody, header, secrets[], nowMs, toleranceSec = 300)`** → `ok | signature_missing | signature_malformed | signature_invalid | timestamp_out_of_tolerance`. It follows stripe-node's `constructEventAsync` (verified in its source):
   - split the header on `,`, then each item at its first `=`, with no trimming;
   - `t` must be 1–12 digits;
   - collect **every** `v1` and ignore other schemes;
   - signed text is `` `${t}.${rawBody}` `` (the raw text, never re-serialised JSON);
   - HMAC-SHA256 keyed with the **UTF-8 bytes of the whole secret string, `whsec_` included** (stripe-node does not base64-decode it);
   - compare with `crypto.subtle.verify` after hex-decoding each candidate; a non-64-hex candidate is skipped;
   - try every secret (current, then the previous one) against every `v1`;
   - the signature is checked before the timestamp.

   **One deliberate difference:** stripe-node accepts any future timestamp. We refuse `|now − t| > 300 s` both ways.

   The `CryptoKey` is cached per isolate by secret (the SES signing-key pattern).

   `stripeTestHeader(rawBody, secret, t)` is exported **for tests and `pay-simulate` only**, with stripe-node's `generateTestHeaderString` algorithm.
2. **`parseStripeEvent(obj)`** → `{id, type, livemode, created, sessionId, techaust: {checkoutId, documentId, env} | null, paymentStatus, status}` or `invalid_event`.
   - Known types map to `ProviderEventType`: `checkout.session.completed` and `.async_payment_succeeded` → `checkout.paid`; `.async_payment_failed` → `checkout.failed` (new member, generic); `.expired` → `checkout.expired`. Anything else → `other`.
   - `techaust` is set only when `data.object.object === "checkout.session"`, `metadata.app === "techaust"` and `metadata.techaust_checkout_id` is a UUIDv7.
   - `eventFacts` is a whitelist: event id, session id, payment-intent id, `amount_total`, currency, `payment_status`, `livemode`, `techaust_checkout_id`. **Never `customer_details`** (name, email, address), any card field or the raw payload (DPDP; ADM-PAY-12).
3. **`sessionRequestOf({checkoutId, documentId, env, amountMinor, documentLabel, description, expiresAt, successUrl, cancelUrl, now})`** → ordered form pairs, or a refusal.
   - `mode=payment`;
   - `line_items[0][price_data][currency]=usd`, `[unit_amount]=amountMinor`, `[product_data][name]=documentLabel` (C9), `[quantity]=1`;
   - `client_reference_id=checkoutId`;
   - `metadata[app]=techaust`, `metadata[techaust_checkout_id]`, `metadata[techaust_document_id]`, `metadata[techaust_env]`, all repeated under `payment_intent_data[metadata]`;
   - `payment_intent_data[description]` (C10, ≤ 1000 characters);
   - `payment_intent_data[statement_descriptor_suffix]=TECHAUST` (C11; ≤ 22; never `statement_descriptor`, which Stripe refuses on card charges);
   - `allowed_payment_method_types[0]=card`;
   - `billing_address_collection=required` (Stripe India export rule; see vendor fact V15);
   - `adaptive_pricing[enabled]=false`, so the client pays the invoice's USD;
   - `branding_settings[display_name]=TecHaust Technologies` (C12);
   - `submit_type=pay`, `locale=auto`;
   - `expires_at` = now + 60 min, in seconds, held within 30 min to 24 h;
   - `success_url` and `cancel_url` carry no token, no session id and no `{CHECKOUT_SESSION_ID}`.

   No `customer`, `customer_email` or `invoice_creation`.

   Refusals: `amount_below_gateway_minimum` (`STRIPE_MIN_AMOUNT_MINOR = 50`, UNCONFIRMED), `expiry_out_of_range`, `label_too_long`.
4. **`readStripeSession(obj)`**: reads a session fetched with `expand[]=payment_intent.latest_charge.balance_transaction` into `{id, status, paymentStatus, livemode, clientReferenceId, metadata, currency, amountTotal, pi: {id, status, amountReceived, currency, metadata} | null, charge: {created, status, captured, methodType} | null, bt: {currency, amount, fee, feeTax} | null}`.
   - Every amount must be a safe integer.
   - `feeTax` is the sum of `fee_details` items whose `type` is `tax`.
5. **`judgeStripeSession(checkoutRow, session, expectedLivemode)`** → `ok` or one verdict:
   - `livemode_mismatch`;
   - `reference_mismatch` (session id, `client_reference_id`, or either metadata set ≠ the row);
   - `currency_mismatch` (anything but `usd` and row currency USD);
   - `amount_mismatch` (`amount_total` ≠ row amount, or the payment intent's `amount_received` ≠ `amount_total`);
   - `not_paid` (`status` complete and `payment_status` unpaid);
   - `not_captured` (payment intent not `succeeded`, or the charge not succeeded and captured);

### C. Admin finance Worker (B2)

**`GatewayEvents.processEvent({eventId})` for provider `stripe`.** The id is our `webhook_events.id`; check against M6.2.
1. The row is not `received` → `duplicate`.
2. The row's facts have no `techaust_checkout_id` → event `ignored`, outcome `not_techaust` (defence in depth; the hook writes no row for these).
3. Find the checkout by provider reference. **No row → review `unknown_link`, no payment row, no bell to the client.** Metadata alone never moves money (L5).
4. `checkout.expired`: re-fetch. If Stripe says `expired`, the row goes `expired` (guarded on `live|stale`). If it says `complete`, go to step 6.
5. `checkout.failed`: the row goes `failed`; the event is processed; no review (the client sees C5 and can try again).
6. `checkout.paid`: **re-fetch**:

   `GET https://api.stripe.com/v1/checkout/sessions/{id}?expand[]=payment_intent.latest_charge.balance_transaction`

   with `Authorization: Bearer`, `Stripe-Version` and `AbortSignal.timeout(8000)`. **`stripeAllowed` runs before any fetch.**
   - network error, 429 or 5xx → `retry`;
   - 404 → review `refetch_failed`;
   - 401 or 403 → review `refetch_failed` with outcome `stripe_permission`, plus a bell.

   Then `judgeStripeSession`.
7. **Export invoice or debit note, ok, still payable** (one batch, M6.2 step 6):
   - payment `stp_<pi>`, confirmed, provider `stripe`;
   - `received_on` = IST day of the charge; mode; `reference_norm`;
   - `charges_minor` 0; the INR columns; `refetched_at`;
   - allocation `min(amount, balance)`, recompute, `ledger_result` last;
   - checkout → `paid`; other live checkouts → `stale`;
   - event → `processed`; audit (actor `webhook`); bells; T11's deed statements;
   - any excess stays as credit, with an `overpaid` review item.

   After the batch, best effort: `POST /v1/checkout/sessions/{id}/expire` on each stale session; success moves it to `cancelled`; logged.
8. **USD proforma, ok, amount ≤ its balance:**
   - payment `pending_verification` with `requested_allocations`;
   - review `advance_blocked` with blocker `fx_rate_needed`, plus a bell (Q1 A);
   - checkout → `paid`; event processed.
   - **No `next: gateway.advance`.**

   The Owner then uses `POST /invoices/:id/advance-invoice` with `paymentId`. The dialog is prefilled (amount, `received_on`, reference) with the rate empty. That route's existing rules apply: the LUT of the receipt day's FY or IGST (`advanceRouteFor`, `LUT_FOR_FY_SQL`), and `fxDateVerdict` against `received_on`. That batch flips the payment to confirmed with the Owner as verifier, which the triggers already allow.

   Above the balance → `proforma_overpaid`.
9. **Mismatch, not payable or anonymised:** as M6.2 step 8 (client known → pending plus a review item of the matching kind; anonymised → `client_gone` only).
   - `not_paid` (async) records nothing; outcome `awaiting_async`; event processed.
   - `checkout_open` → `retry`, at most 3 times, then `refetch_failed`.

**`GatewayEvents.refreshCheckout({checkoutId})`:** the same re-fetch and processing with source `refresh`. It never moves a row to `expired` on our clock alone; only Stripe's word does (L6).

**`PortalPayments.createLink({…, provider: "stripe"})`:** M6.2's SQL re-checks of who may pay, with the Stripe row of the table, then:
1. **Open checkout for this document:**
   - same amount and ≥ 20 min left → reuse its stored URL;
   - otherwise `POST …/{id}/expire`. Answers:
     - success → `cancelled`;
     - Stripe refuses because the session is `complete` → run refresh and answer 409 **`payment_processing`**;
     - already `expired` → `expired`.
2. **Row first:** INSERT `creating`. The unique index serialises double clicks (409 `link_in_progress`).
3. `POST /v1/checkout/sessions` with `sessionRequestOf` and **`Idempotency-Key: <checkout id>`**.
4. Then `live`, storing the session id and URL.
5. A `creating` row older than 60 s is **adopted** by repeating the same request with the same key and the same stored `expires_at` (Stripe returns the same session within 24 h).
6. Create error 4xx → `failed` and 502 `gateway_error`.

Other answers: 10 per client per hour → 429; `amount_above_maximum` (`maximumMinor`); a live key → 503 `live_not_allowed` with **zero fetches**.
