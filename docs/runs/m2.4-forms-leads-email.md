## Before the build (2026-10-23)
- M2.3 approved and merged (PR #47–#49). The site shell, the content files, the link checker (with `/contact` and `/get-a-quote` on its allow-list for this milestone) and the content lint are on `main`.
- **Owner (2026-10-23):** approved the M2.4 plan, including the two-layer rate limit (below). A visitor without JavaScript gets the **email fallback**: the form still shows, with a note that it needs JavaScript for spam protection and the address contact@techaust.com; a submission without a Turnstile token gets a page saying the same.
- **Lead decisions (rows in 13):**
  - **Rate limit in two layers.** The Workers Rate Limiting binding counts only over 10 or 60 s, and the web Worker has no D1. So: `RL_FORMS` on the web Worker allows 2 submissions per 60 s per address (429 beyond); the jobs consumer enforces FRM-02's exact 5 per 10 min and 50 per day per address against D1. A message over those limits **creates no lead and sends no email**; only a counter moves and a log line without personal data is written (keeping a spammer's details has no purpose under DPDP). FRM-02's acceptance "the 6th request in 10 min gets 429" becomes "the 6th creates no lead and no email".
  - **The address is never stored raw.** The web Worker computes `ipHash = HMAC-SHA-256(FORMS_IP_PEPPER, CF-Connecting-IP)` and puts only that on the queue message; the jobs Worker counts by it and writes it into the consent receipt.
  - **Emails go through the `email` queue.** The leads consumer creates the lead and enqueues two messages on `EMAIL_QUEUE`; the email consumer renders, sends with SES and writes `email_log` (05 §11.1). So every later sender (magic links, staff alerts, invoices) reuses one path.
  - **Staging and local never email strangers.** Local uses a `log` transport (no network). Staging sends only to addresses in the `EMAIL_ALLOWED_RECIPIENTS` var (the owner's verified test inboxes; SES sandbox); any other recipient is logged as `skipped` in `email_log`, not retried.
  - **Split out (M2.4b, after this):** delivering the portal magic link from `no-reply@`, the staff security emails (login alert, lockout, 2FA change), and Turnstile on the admin and portal sign-in forms. They touch the auth code (Tier A areas) and get their own brief.
  - **Later (M7.2):** SES bounce and complaint events (EventBridge → hooks), which then fill `email_suppressions`. M2.4 creates the table and checks it before sending.

### Step 1: builder (Sonnet 5.5, medium)
**First step:** load `cloudflare:workers-best-practices`, `cloudflare:wrangler`, `cloudflare:cloudflare` and `cloudflare:turnstile-spin` (read it for siteverify only; do not run its wizard or any script that calls Cloudflare), and `aws-core:aws-messaging-and-streaming` (SES; if it routes you to an `amazon-ses` skill that can't load, say so). List them in the report.

Data, logic, Workers and tests; no page markup or CSS (the designer's step).

1. **Schema (`packages/db`):** new tables `email_log` and `email_suppressions` exactly as 05 §5.2 lists them (`email_log` idx(entity_type, entity_id) and an index on `status`; `email_suppressions` primary key `email`, lower-cased). Form counters reuse `auth_attempts` with keys `f:10m:<ipHash>` and `f:day:<ipHash>` if its columns fit; if they don't, stop and report rather than altering it. `pnpm db:generate`; a new migration only (never rebuild an existing table; `scripts/check-migrations.mjs` must pass).
2. **Shared rules (`packages/core`):** the form schemas in `schemas/forms.ts` already exist; add only what's missing: the queue message schemas (`LeadMessage` = form kind + validated payload + `ipHash`, `formVersion`, `noticeVersion`, `sourcePage`, `referrerHost`, `utm`, `currency`, `submittedAt`; `EmailMessage` = `{template, to, data, entity}`), the lead reference generator (`L-` + 5 characters of Crockford base32 from `crypto.getRandomValues`, no I/L/O/U; unique, not sequential), and the CR/LF stripping used for any header value. FRM-01's test: decimals, empty optional fields and Unicode names pass; oversize and control characters fail. Keep core at ≥ 90 % coverage.
3. **Web Worker (`apps/web/src/worker.ts`):** `POST /api/forms/contact` and `POST /api/forms/quote` (replace the 501 stub; both stay in `run_worker_first`). In this order: POST only → `Content-Type` is `application/x-www-form-urlencoded` or JSON → body ≤ 16 KB read as a stream with a hard cap (413) → Origin is `https://techaust.com` or the staging host or, locally, `http://localhost:4321` (403) → `RL_FORMS.limit({key: ipHash})` (429 with `Retry-After`) → honeypot field empty and elapsed time ≥ 3 s from the form's start-time field (generic 400) → Turnstile siteverify with `remoteip`, fail closed on network errors, and require `success`, the expected `action` (`contact` / `quote`) and a hostname from `TURNSTILE_HOSTNAMES` (generic 400) → zod with the shared schema → `LEADS_QUEUE.send(message)` → `{ok: true, ref}`. The ref is made here so the visitor sees it at once; the consumer keeps it (on the rare unique clash it makes a new one and the acknowledgement email carries that one).
   - Errors are only `{ok: false, error: "<code>"}` (no detail beyond a field list for zod failures). A JSON request gets JSON; a plain form POST gets a 303 to `/thanks?ref=…` on success and to `/contact?error=…` or `/get-a-quote?error=…` otherwise. A form POST **without a Turnstile token** (no JavaScript) redirects to the page's no-JS notice (owner decision; the designer builds the notice).
   - Bindings and secrets in `apps/web/wrangler.jsonc` (top level and each env, since bindings aren't inherited): `LEADS_QUEUE` producer (`techaust-staging-leads` on staging; production gets no resources until Phase 7, so leave the production env without it and say so in the comment), `RL_FORMS` (`ratelimits`, 2 per 60 s), vars `TURNSTILE_HOSTNAMES`, `TURNSTILE_SITE_KEY` (public), secrets `TURNSTILE_SECRET`, `FORMS_IP_PEPPER` in `secrets.required`. `scripts/check-web-bindings.mjs` must still pass (queues and rate limits are allowed); add a test that it still rejects D1/R2/KV/DO/Hyperdrive. Local `.dev.vars.example` names only; `pnpm dev:secrets` writes local values and Turnstile's always-pass test keys.
   - CSP: the form pages need `https://challenges.cloudflare.com` in `script-src` and `frame-src` (and `connect-src` if the widget needs it); change only those two pages' headers, and the CSP-hash check must still pass.
4. **Jobs Worker (`apps/jobs`):**
   - **Leads consumer** (`techaust-staging-leads`, batch 5, concurrency 1, 5 retries → `techaust-staging-leads-dlq`): per message, one unit of work: validate the message with the core schema (an invalid message is acked and logged, never retried), move the two counters atomically in one `db.batch()` and stop quietly when over 5 per 10 min or 50 per day, insert the lead (`source = web`, `form_version`, the consent receipt `{noticeVersion, purposes, at, ipHash, marketing}`, attribution, `delete_after` from the `retention.leadsMonths` settings default), then enqueue the acknowledgement (to the visitor, from `hello@`, Reply-To `hello@`) and the internal alert (to `LEAD_ALERT_TO`). Idempotent: a redelivered message never makes a second lead or a second pair of emails (use the ref as the key).
   - **Email consumer** (`techaust-staging-email`, batch 5, concurrency 2, 5 retries → `-dlq`): check `email_suppressions` and `EMAIL_ALLOWED_RECIPIENTS` (staging) → render → send → `email_log` (`queued` → `sent` / `skipped` / `failed`). A permanent SES error (4xx other than throttling) is logged `failed` and acked; throttling and 5xx retry.
   - **DLQ consumers** for both DLQs: write one log line without personal data and an internal alert email to `LEAD_ALERT_TO` ("A lead or email failed after 5 tries: open the admin"), sent directly through `packages/email` so a broken email queue can't swallow it. (`review_items` arrives with the feature that uses it.)
   - Bindings: the two queue consumers and DLQ consumers, `EMAIL_QUEUE` producer, vars `LEAD_ALERT_TO`, `EMAIL_ALLOWED_RECIPIENTS`, `EMAIL_TRANSPORT` (`log` locally, `ses` on staging), `SES_REGION` = `ap-south-1`, `SES_CONFIGURATION_SET` = `techaust-transactional`; secrets `SES_ACCESS_KEY_ID`, `SES_SECRET_ACCESS_KEY` in `secrets.required`. `wrangler types` afterwards.
   - CPU: each message stays within the Free plan's 10 ms (target p99 ≤ 7 ms); say how you checked.
5. **`packages/email`:** the SES v2 client (`SendEmail` via aws4fetch 1.0.20, already the approved pin in 05 §2; if it isn't installed yet, adding that exact version is approved by 05 and 13 2026-10-06, otherwise stop and ask), the `log` transport, header sanitising (CR/LF stripped, display names quoted), and the two template slots `lead.acknowledgement` and `lead.alert` as typed functions returning `{subject, html, text}`. The builder writes plain placeholder HTML only; the designer replaces it with the real layout (step 2). Subjects and text bodies word for word from 07 §8.
6. **Tests (Vitest; workerd for Workers):**
   - abuse: a 17 KB body → 413; a foreign Origin → 403; wrong method or content type; a missing or failing Turnstile token, a filled honeypot or a too-fast submission → the same generic 400; `\r\n` in the name never reaches a header; error JSON has only `ok` and `error`; the 3rd request in 60 s → 429 (binding mocked); the no-token form POST → the no-JS redirect
   - pipeline: submit → queue message (no raw IP anywhere) → lead row with consent receipt and attribution → two email messages → `email_log` rows; the 6th submission in 10 min from one `ipHash` and the 51st in a day make no lead and no email; a redelivered message makes no duplicate; a suppressed or (staging) non-allowed recipient → `skipped`; a permanent SES error → `failed`, a 5xx → retry; the DLQ path sends the alert
   - the reference: format, alphabet, no collisions in a large sample (fast-check)

**Done:** `pnpm check` and `pnpm test` green through `bash tools/heavy.sh`; commit; push your branch; append "Builder report" here (files, commands and results, what you couldn't verify, open questions, the skills loaded); stop. Stop any `wrangler dev` you started.
