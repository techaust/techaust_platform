## Seven findings in the M5.1 code that shape this brief (analyst)
1. `document_triggers` (0032) builds its freeze list from the live schema (`frozenDocumentColumns()`, `packages/db/src/triggers.ts:71,419`), and the drift test (`packages/db/test/triggers.test.ts:513-538`) regenerates it: any ADD COLUMN on `documents` breaks 0032. Pin 0032's lists (LD35).
2. The M5.1 issue batch marks a milestone `invoiced` on any issue, including a proforma (`issue.ts:330-336`): a proforma would hide the unbilled milestone and the 25-day warning could never fire. The milestone move must depend on the type.
3. The content hash (`contentHashInput`, `packages/core/src/documents.ts:270-324`) doesn't cover the exchange rate, so an approval isn't tied to it (LD24).
4. The LUT setting is one object today (`tax.lut {arn, fy}`, `schemas/settings.ts:121-124`), read by `lutsOf` (`tax/supply.ts:42`); stored rows must keep parsing and a stored LUT must not vanish.
5. `realisation_due_at` is frozen at issue (`FROZEN_COLUMNS_0001:117`) and nothing sets it (LD26).
6. A tax invoice for a payment already received would be chased for payment (balance = total → Overdue, M5.4 reminders): the Q9 action marks it paid (LD22).
7. The jobs Worker must not import `@techaust/core/settings` (zod): the cron's LUT check needs a reader without zod.

## Lead decisions (docs/13, 2026-10-27)
- **LD22** The Q9 action is the only place M5 writes paid amounts: the new invoice is paid with balance 0, the proforma's paid and balance move, the evidence is an `advance_receipts` row; M6 takes those rows into `payments`; M5.5 statements must not count a proforma and its invoice twice.
- **LD23** The endorsement is fixed text in core, frozen and sealed; the `export_declaration` block becomes an optional extra note pinned by `export_declaration_id` (a Settings › Terms hint needs a 07-S line).
