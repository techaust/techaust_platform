### Lead decisions for this build (recorded in docs/13)
1. **Client codes:** `C` + a 4-digit sequence (`C0001`), the next free number taken in the conversion batch; the existing `clients_code` unique index guards a race (retry once on conflict). The sample clients keep `SAMPLE-A` / `SAMPLE-B`.
2. **New lead columns by `ALTER TABLE leads ADD COLUMN` only** (`leads` is referenced by `lead_activities`, so it is never rebuilt): `duplicate_of` (the earlier lead with the same email within 30 days) and `proposal_id` (the draft made at conversion). Anything beyond `ADD COLUMN`, a new table, index or trigger: stop and report.
3. **Stage automation:** "Proposal sent" and "Won" follow the linked proposal once proposals can be sent and accepted (M4.2/M4.3). M3.2 builds and tests the one function those milestones call (proposal sent → `proposal_sent`; accepted → `won`, unless a person has set a later manual stage), and the manual moves with their rules now.
4. **Retention clean-up:** a daily cron at 03:30 IST (22:00 UTC) in the jobs Worker that **only enqueues** (JOB-CRON-01), one lead per message on the **existing** `LEADS_QUEUE` as a new message kind (no new queue, no hosted change). A lead is due when it is not converted (`client_id` null), has no legal hold and `delete_after` has passed; `delete_after` = last activity + `retention.leadsMonths`, recomputed on every activity. The consumer re-checks those conditions before deleting. **A dry-run mode is on everywhere until the owner says otherwise** (a `LEAD_PURGE_MODE` var, `dry_run` locally and on staging, no production value until Phase 7): it writes what it would delete to the log (lead ref only) and deletes nothing.
5. **Reply from admin (ADM-LEAD-06):** through `EMAIL_QUEUE` and `email_log` like every other email, from `hello@` with Reply-To `hello@`; free text is sent as plain text and escaped in HTML. The ready-made templates come from 07-I, drafted by the lead for the owner's word-for-word approval; until then only free text is offered and the template list is empty.

### What to build (API, data, jobs and checks; no screens: the designer builds them afterwards)
1. **Schema.** The two `ADD COLUMN`s (decision 2), their indexes, and whatever else the work below needs as new tables, indexes or triggers only. `pnpm db:generate` must produce the migration; check it with `scripts/check-migrations.mjs`.
2. **Routes and permissions (ADM-G-02).** Every route a `ROUTES` row with its matrix action (`leads.read`, `leads.write`, `clients.write` + `proposals.draft` for conversion; add a matrix row only if docs/04 §9 needs one and say so) and its audit action; a test per route per role (allowed / denied).
3. **Leads list (ADM-LEAD-02):** `GET /leads`, keyset (25/50), filters stage, owner, source, service, "next action overdue", "scheduled for deletion" (due within 14 days); sort by created, last activity or next action; search by name, email, company or ref (prefix, on indexed columns, no full scans). A board query that returns the counts per stage and the first page of each stage.
4. **Lead page (ADM-LEAD-03):** `GET /leads/:id` with its timeline (`lead_activities`, keyset), the linked duplicate(s), client and proposal; `PATCH /leads/:id` for owner (assignee), next-action date and note, contact fields (optimistic concurrency on `updated_at`, 409 `stale_version`); `POST /leads/:id/notes`. Every change writes a timeline row and an audit row (before → after, changed fields only) and refreshes `last_activity_at` and `delete_after`.
5. **Stages (ADM-LEAD-02):** `POST /leads/:id/stage {stage, lostReason?}`: "lost" needs a reason from `LOST_REASONS` (the DB CHECK already demands it; answer 400 first); leaving "lost" clears it; "won" by hand is the manual override. Plus the stage-automation function of decision 3, exported for M4, with its tests.
6. **Manual leads (ADM-LEAD-01):** `POST /leads` with `source = manual`, the lead ref made the same way as the jobs Worker (move the ref maker to a shared place if needed; refs stay non-sequential, FRM-07), and the **duplicate link** (same email, lower-cased, within 30 days → `duplicate_of`; linked, never merged), also applied in the jobs lead insert in the same `db.batch()`. The new-lead bell row (M3.1) for manual leads too, except for the person who created it.
7. **Convert (ADM-LEAD-04):** `POST /leads/:id/convert` with the client fields the lead lacks (type, country, GST status, GSTIN when registered, validated with `packages/core/src/gstin.ts`, currency), pre-filled from the lead. **One `db.batch()`:** the client (decision 1), its primary contact (from the lead), a `documents` row of type `proposal`, status `draft`, for that client and currency, no number (numbers come only at issue), the lead's `client_id` and `proposal_id`, stage unchanged, a timeline row, and the audit rows. A converted lead can't be converted again (409). Test atomicity: make one statement fail and prove nothing was written. The service the lead asked for travels to the draft in the least-risk way the documents schema allows today; if it needs a change to an existing table, stop and report.
8. **Retention clean-up (ADM-LEAD-05, decision 4):** the cron handler (enqueue only, keyset over `leads_delete_after`, ≤ 5 ms CPU, at most one page per run with a cursor carried in the messages if more are due), the consumer (one lead per message, re-check, delete the lead; `lead_activities` cascade; delete or detach its bell rows; one audit row with the lead ref only, no personal data), the dry-run mode, and an idempotent re-delivery. `delete_after` is backfilled for existing leads by the migration or the first run (say which). Tests: due / not due / converted / legal hold / dry-run / redelivery / a lead that got an activity after it was enqueued.
9. **Reply from admin (ADM-LEAD-06, decision 5):** `POST /leads/:id/reply {subject, body, templateId?}` → one `EMAIL_QUEUE` message to the lead's email, logged in `email_log` and on the timeline (subject and a short excerpt only). Rate-limit per member (a sensible count per hour, stated in the report). The template list endpoint returns what `packages/email` registers (empty until 07-I is approved). Staging's `EMAIL_ALLOWED_RECIPIENTS` still applies.
10. **L-d (M3.1 follow-up):** the numbering settings write checks "series issued this FY" inside the same batch as the write (a conditional statement or trigger, not a read-then-write), answers 409 `series_in_use`, and a save that changes nothing answers 200 `changed: false` without a version bump. VERIFY WITH CA/LEGAL stays on the lock rule.
11. **Search (ADM-G-05):** leads already appear; add the ref and company to the match if they're indexed, nothing else.

**Rules:** CLAUDE.md conventions (UTC ms, keyset ≤ 50 rows, index every filter, one unit of work per queue message, cron only enqueues, p99 CPU ≤ 7 ms); every mutating route writes an audit row and a test proves it (ADM-G-06); no personal data in logs (refs and ids only); retention and DPDP items tagged VERIFY WITH CA/LEGAL; existing tests pass unchanged unless a change is intended (name each); heavy commands via `bash tools/heavy.sh --log <name> …`; commit every 20 minutes and at each finished layer; the whole-repo lint once, at the end.
