### What to build (API, data and checks; no screens: the designer wires the screens afterwards)

2. **Settings API (ADM-SET-01…10):** `GET /settings` (the groups the role may see), `GET /settings/:group`, `PUT /settings/:group` with the shared zod schema; optimistic concurrency on the row's `version` (409 on a stale version); every change writes an audit row with a before → after diff of the changed fields only, sensitive fields masked (ADM-G-06, ADM-AUD-01). Per group:
   - **company (SET-01):** extend `companySettings` with what the PRD lists and the schema lacks: PAN derived from the GSTIN (computed, read-only, never typed), principal place of business, the logo choice. **Logos (lead decision, no hosted change):** the light and dark logo are chosen from the generated brand files in `packages/ui/brand` (a fixed list), not uploaded; the optional signature image and custom uploads wait for R2 (M3.4 files).

Edits need step-up (`bank.manage`); the accountant reads masked (`bank.readMasked`). The number never appears in logs, audit summaries (masked there) or error bodies; a test searches the captured logs and audit rows for the fixture number.
   - **tax (SET-03), numbering (SET-04):** existing schemas. Numbering: the format validator (≤ 16 characters, A–Z 0–9 `/` `-`) on every series; a series that has issued a number this FY keeps its format read-only, and the next number can't be decreased (the `doc_counters` trigger guards the DB; the API answers 409 with a clear code first). Changes affect new documents only.
   - **payment terms (SET-05):** existing schema; add only the PRD items with no field yet (e.g. the Razorpay minimum partial amount); the advance mode already lives in tax, don't duplicate it.
   - **gateways (SET-06):** new schema: per provider (as listed in docs/05) a mode `test | live` and a status `configured | missing` computed from whether the secret names exist in `env` (never read out or return a value). `PUT` to `live` is rejected while `PAYMENTS_LIVE_ALLOWED !== "true"` (test). Step-up (`gateways.manage`).
   - **email (SET-07):** new schema: sender identities (hello@, billing@, no-reply@), reply-to, BCC-to-owner per template, footer text. `POST /settings/email/test-send {template}` queues one email **to the signed-in member only** through `EMAIL_QUEUE` (the existing jobs path, fixture data; the recipient comes from the session, never the body). Staging's `EMAIL_ALLOWED_RECIPIENTS` still applies.
   - **terms (SET-08):** versioned text blocks (append a new version, never edit one; `sha256` of the body; "used by N documents" from `documents.terms_version_id`).
