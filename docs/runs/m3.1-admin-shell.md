## Phase 1: design preview (designer, Opus 5.5 high)
**Goal:** the owner sees and approves the look and behaviour of the admin shell and its key screen types before they are built for real. Everything else in admin copies these.

**Branch:** `feat/m3.1-admin-shell` (holds this brief). The designer creates `feat/m3.1-preview` from `origin/feat/m3.1-admin-shell` in its own worktree and pushes only that; the lead merges.

**First step:** load `frontend-design:frontend-design` (mandatory for screens) and any other fitting skill (docs/14 §9); list them in the report.

**Where:** real React components in `apps/admin/src` (so an approved preview becomes the start of the build), shown on **dev-only** routes `/preview/*` that are never in the production build (prove it: the built bundle has no preview route or sample data). **Sample data only**, every screen visibly labelled "Preview — sample data"; made-up names on `example.test` addresses; a fake GSTIN that is clearly marked as a sample (never a real one); no API calls, nothing saved.

**Screens (06 §5.3, §5.4, §5.5; PRD ADM-G-01…09, ADM-SET-01…10, ADM-AUD-02):**
1. **Shell** (`/preview/shell`): `AppShell` with the left nav in the PRD's order (Dashboard, Leads, Clients, Projects, Care plans, Time, Catalogue, Proposals, Estimates, Invoices, Payments, Reports, Approvals, Audit log, Settings), collapsible, current item marked; the top bar with global search (a sample results popover grouped by type), the notification bell (sample list: "New lead", unread state, each linking to its record), the account menu (name, role, "Your account", "Sign out"); theme (system/light/dark). A "coming soon" `EmptyState` for a section owned by a later milestone (say what arrives and when, no promised dates).
2. **Users list** (`/preview/users`): `PageHeader` + `DataTable` (keyset paging "Next/Previous", sort, `FilterBar` with role and status chips kept in the URL, search), `StatusPill` for active / invited / deactivated, row actions (change role, deactivate, reactivate, resend invite) with `ConfirmDialog`; the invite dialog; cards below `md`; the empty and loading (`Skeleton`) states.
3. **Settings** (`/preview/settings`): the settings navigation for all 10 groups (ADM-SET-01…10), with two groups fully designed:
   - **Company profile** (SET-01): fields with `FormField`, the GSTIN with its live check (valid / wrong format / wrong check character) and the derived PAN read-only, state and code, logos, an unsaved-changes warning, `ErrorSummary` on submit.
   - **Bank details** (SET-02): INR and USD/SWIFT blocks, numbers masked (last 4 shown), "Edit" asks for the 6-digit code again (`StepUpAuth` in a dialog) before the fields unlock; a note that only the owner enters these.
   - for the other 8 groups: their layout pattern only (one example each of a toggle, a select, a number with unit, a versioned text block with "version 3, used by 12 documents"), labels from the PRD; tax and retention groups carry a visible "VERIFY WITH CA" / "VERIFY WITH CA/LEGAL" note; Gateways shows mode test/live with live disabled and "configured / missing", never a key field.
4. **Audit log** (`/preview/audit`): `ActivityTimeline` / table of who, what, when (IST, relative + absolute), a before → after diff for a settings change, filters by actor, action and date.
5. **States** (`/preview/states`): `Toast` (success and error), `ConfirmDialog` with a step-up slot, form errors, a 403 "you don't have access" page, a 404 inside the shell.

**Rules:** tokens only from `packages/ui` (no hard-coded colours, sizes or fonts; the generated logo files, never hand-drawn; the wordmark never in a live font; arrows as icons); plain CSS with the token custom properties like the existing `app.css` (no new packages: stop and report if one seems needed); keep what M1.5 already built (sign-in, account, users screens, `dialog.tsx`, `step-up-dialog.tsx`, `confirm-dialog.tsx`) consistent or improve it in place; WCAG 2.2 AA, 44 px targets, text ≥ 12 px / body ≥ 16 px, visible focus, reduced motion; keyboard: the nav, menus, popovers and dialogs work and return focus; English (India/UK spelling); no banned phrases (07 §1.3); money via `@techaust/core` formatting; dates in IST. The owner's taste: flat ink/verdigris brand geometry, calm and dense enough for daily work; generic soft/3D/stock-dashboard looks are rejected.

**Screenshots** (`.logs/m3.1-preview/`, git-ignored): each preview screen at 375, 768, 1280 and 1920 px, light and dark; the search popover, bell list, account menu and a dialog open; keyboard focus on the nav; the collapsed nav.

**Checks:** `pnpm check`, `pnpm --filter @techaust/admin build` (via `bash tools/heavy.sh --log …`) with proof that `/preview` and the sample data are not in `dist`, a scripted a11y pass (axe on each preview screen in both themes, 44 px, names, focus), the admin JS size before and after.

**Stop after the preview:** commit, push `feat/m3.1-preview`, append "Designer report: preview" here (screens, components, screenshot list, a11y results, JS size, every placeholder, deviations from 06, open questions, whether you recommend any package for the build and why), stop any dev server, and stop. **Nothing further is built until the owner approves** (a decision row in 13).
